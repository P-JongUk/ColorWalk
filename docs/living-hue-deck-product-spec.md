# Living Hue Deck 제품 명세

마지막 갱신: 2026-07-26 KST  
상태: **approved — 첫 출시 대표 개인 콘텐츠**  
상위 기준: `docs/hueday-product-blueprint.md`, `docs/launch-scope-and-update-safety-contract.md`

## 1. 한 문장 제품 계약

> Living Hue Deck은 사용자가 그림을 그리거나 꾸미기 숙제를 하지 않아도, 매일 찾은 색과 사진이 1·3·5·8장의 기록에 따라 스스로 자라며 쌓이는 개인 컬러 아카이브다.

Color Hunt의 본질은 현실에서 색을 찾는 일이다. Deck은 그 행동의 결과를 “내가 모은 하루와 색”으로 보이게 하는 보상이며, 별도의 게임을 강요하거나 사진 촬영보다 더 많은 노동을 요구하지 않는다.

## 2. 첫 출시에서 확정된 경험

### 기록 한 장의 성장

각 날짜의 고정된 미션 색과 그날 저장한 사진은 하나의 Deck 카드가 된다. 1–7장도 모두 유효한 일일 기록이며, 8장만 3×3 완성 및 주요 보상 단위다.

| 사진 수 | 카드 의미 | 사용자가 느껴야 할 변화 |
| --- | --- | --- |
| 1장 | 색 씨앗 | 오늘 처음 찾은 색과 첫 장면이 남는다. |
| 3장 | 기록의 윤곽 | 카드 프레임/짧은 색 이름이 생겨 “모으고 있다”는 느낌을 준다. |
| 5장 | 질감의 축적 | 사진 조각과 가벼운 패턴이 풍성해진다. |
| 8장 | 유리 봉인 카드 | 3×3 한 페이지 완성, 주요 보상·완성 카드·공유 결과가 된다. |

- 1·3·5 단계는 시각적 성장일 뿐 실패나 잠금의 기준이 아니다.
- 8장은 사용자를 벌주지 않는 “한 페이지 완성”의 기준이다.
- 연속 출석, 점수, 희귀도 뽑기, 시간 제한, 친구 순위는 넣지 않는다.
- 카드 상태는 기존 일일 기록과 3×3 사진 수에서 **결정적으로 파생**한다. 같은 데이터를 별도 카드 이미지나 중복 서버 레코드로 먼저 저장하지 않는다.

### Color Volume

- 같은 미션 색의 완성 3×3은 각각의 날짜 카드로 남고, 함께 해당 색의 `Color Volume`을 이룬다. 같은 색을 반복해서 찾는 것은 손실이 아니라 축적이다.
- 같은 색은 대소문자를 정규화한 유효한 6자리 `mission_hex`가 같을 때만 같은 Volume으로 묶는다. 색 유사도나 색상군 분류는 사용하지 않는다.
- 상황 컬렉션은 M3에서 추론하지 않는다. 하나의 일일 카드에 여러 시간·날씨의 사진이 섞일 수 있으므로, M4에서 명시적인 미션 팩 ID가 저장된 뒤 최대 3개를 제공한다.
- 각 카드·색에서 원래의 3×3, 날짜, 저널로 돌아갈 수 있어야 한다. 예쁜 카드가 원본 기록을 가리는 독립 게임이 되면 안 된다.

### 주간 회고와 공유

- 주간 `Hueprint` 또는 `Color DNA`, 월간 `Color Capsule`은 M5에서 같은 원본 데이터 위에 구현한다.
- M3 카드에서는 기존 원본 Post의 Story Studio를 연다. 별도 Deck 이미지 포맷이나 업로드를 만들지 않는다.

## 3. 시각·상호작용 기준

- 앱 외부 UI는 승인된 **D — Chromatic Archive**의 모던하고 정돈된 언어를 유지한다.
- 카드는 사진과 미션 색이 주인공이다. 8장 완성에서만 절제된 반투명 유리 봉인감을 사용한다.
- 수집 카드가 포켓몬·가챠·유아용 스티커 게임처럼 보이지 않게 한다. 강한 희귀도, 랜덤 보상 상자, 과도한 배지 밀도는 금지한다.
- 날씨·시간·계절은 카드의 가벼운 질감/카피를 바꾸는 문맥으로만 쓴다. 정확한 위치, 주소, 학교/카페 추론, 감정 판정은 저장하거나 표현하지 않는다.
- 430×932에서 시작, 1/3/5/8, Color Volume, 원본 3×3, 기존 Story 내보내기를 하나의 여정으로 확인한다.

## 4. 최소 기술 계약

- 첫 구현은 기존 `posts`, `grid_images`/`client_meta.gridImages`, Color Hunt 메타데이터와 저널을 읽어 카드 UI를 파생한다.
- 카드 룩은 공통 CSS/SVG/Canvas 규칙과 미션 HEX·사진 수·안전한 문맥 값으로 결정한다. HEX별 이미지 에셋이나 생성형 AI 결과를 미리 저장하지 않는다.
- 로컬 원본/master, 저화질 preview, 기존 동기화/복구 계약을 침해하지 않는다. 원본 사진은 Deck 렌더링이나 분석 이벤트로 새로 업로드하지 않는다.
- 초기 출시에는 별도 Deck 테이블, 서버 렌더링, 실시간 동기화, 카드 거래/교환, 랭킹을 만들지 않는다. 실제 데이터가 이 구조로 부족하다는 증거가 생길 때만 additive 변경을 검토한다.
- 앱 업데이트는 구버전의 기존 일일 기록을 계속 읽을 수 있어야 하며, 로컬 데이터 형식 변경은 copy-forward 후 검증하고 이전 레코드를 제거한다.

## 5. 보상·측정 기준

- 보상: 8장 완성 → 완성 카드/Color Volume 누적/기존 3·7·14·30 완료 페이지 배지/후속 창작 재료.
- 유지 동기: “다음 사진이 내 카드를 어떻게 바꿀지”, “같은 색의 Volume을 한 장 더 채우고 싶다”, “이번 주 색 흐름을 보고 싶다”여야 한다.
- M3의 최소 측정은 Deck 진입, 한 Deck 세션당 실제 보인 카드 상태(1/3/5/8), 원본 3×3 재진입, Volume 진입, Deck에서 Story 열기다. 기존 Story export/share는 실제 callback 실행 시에만 기록한다. 사진·정확 위치·저널 본문·HEX·경로는 payload에 넣지 않는다.
- 성공 여부는 8장 강제 완성률만으로 판단하지 않는다. 부분 기록 재방문, Deck/원본 재진입, 주간 회고 열기, Story 내보내기의 흐름을 함께 본다.

## 6. 명시적 제외와 보류

- **Hue Canvas**: G1 프로토타입은 `feature/hue-canvas-prototype`과 D 드라이브 참고 자료에 보존한다. 첫 출시에는 넣지 않지만 출시 후 가능한 한 빠르게 제공할 필수 초기 업데이트로 승인됐다. production 구현은 Deck/Color Hunt 데이터를 변경하지 않고 Palette를 파생하며, 업데이트 안전 gate를 먼저 통과한다.
- 사진을 자동 도안으로 바꾸는 생성형 AI: 현재 보류다. 비용·대기 시간·개인정보·결과 품질을 감수할 이유가 검증된 뒤에만 후보로 재검토한다.
- Hue Charm, Hue Loom, Hue Bouquet 등은 후보 아이디어다. Living Hue Deck의 우선순위를 빼앗지 않는다.
- 친구/공동 기능은 첫 출시 범위가 아니다. `Hue Drop`은 출시 후 첫 번째 업데이트 후보이며 `docs/hue-drop-post-launch-spec.md`를 따른다.

## 7. 변경 방지 규칙

Deck을 Canvas, 방 꾸미기, 랜덤 수집 게임, 공개 SNS 피드로 바꾸거나, 8장 전의 기록을 무효로 만들려면 현재 계약·충돌 근거·사용자 영향·최소 두 선택지를 먼저 제시하고 사용자의 명시 승인을 받아야 한다.
