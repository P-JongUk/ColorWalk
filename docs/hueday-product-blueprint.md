# Hueday 전체 제품 청사진

마지막 합의 정리: 2026-07-22 KST
문서 역할: 지금까지 사용자와 Codex가 합의한 Hueday 전체 방향을 한곳에서 확인하는 최상위 제품 source of truth
상세 실행 순서: `docs/hueday-development-roadmap.md`

## 1. 제품 한 문장

> Hueday는 오늘의 미션 색을 일상에서 발견해 3x3으로 모으고, 그 색으로 나만의 공간과 색 정체성을 키워 친구와 가볍게 나누는 카메라 기반 컬러 다이어리다.

Hueday는 산책 기록 앱, 사진 SNS, 꾸미기 게임 중 하나만을 목표로 하지 않는다. 현실의 작은 관찰을 `컬러 헌트`, `개인 공간`, `회고`, `공유`로 이어 주는 하나의 경험을 만든다.

## 2. 출시 원칙

- 최대한 빠르게 출시한다.
- 빠른 출시를 핵심 요소를 잘라낸 최소 앱으로 해석하지 않는다.
- 성공 가능성을 만드는 실현 가능한 요소는 완성도 있게 포함한다.
- 구현·운영·심사 난도가 출시 가치에 비해 지나치게 큰 기능만 근거를 남기고 후순위화한다.
- 속도를 이유로 인증, RLS, 데이터 손실 방지, 개인정보 보호, 접근성, 실기기 QA를 생략하지 않는다.
- 날짜를 임의로 늘여 잡는 장기 일정 대신 의존 관계가 있는 critical path를 따른다.

## 3. 사용자와 감정 목표

### 주요 사용자

- 한국의 10대와 20대 초반 베타 사용자
- 사진을 올리고 싶지만 얼굴·외모·인기 비교에는 피로한 사람
- 다이어리를 매일 길게 쓰기 어렵지만 작은 기록은 남기고 싶은 사람
- 색, 무드, 사진, 꾸미기, 수집을 좋아하는 사람
- 학교, 통학, 카페, 집, 여행 같은 일상을 새롭게 보고 싶은 사람

### 사용자가 느껴야 하는 감정

- `오늘은 이 색이 어디에 있을까?`라는 작은 호기심
- 평범한 일상에서 색을 찾아낸 기쁨
- 3x3 한 페이지를 채우는 완성감
- 내 색으로 아이템과 공간이 생기는 소유감
- 시간이 쌓일수록 나만의 색 흔적이 선명해지는 정체성
- 친구와 비교하지 않고 같은 색을 서로 다르게 발견하는 친밀함

### 만들지 않을 감정

- 하루를 놓쳐서 모든 기록이 무너졌다는 실패감
- 친구보다 점수가 낮다는 비교 불안
- 펫이나 방을 방치했다는 죄책감
- 색 일치율이 낮아 틀렸다는 평가
- 사진을 공개하지 않으면 기능을 쓸 수 없다는 압박
- 결제하지 않으면 내 기록을 잃는다는 불안

## 4. Hueday의 고유 핵심 루프

```text
오늘의 상황에 맞는 미션 팩
→ 중앙에 제시된 미션 색
→ 일상에서 비슷하다고 느끼는 색 찾기
→ 주변 8칸을 사진으로 채운 3x3 컬렉션
→ 짧은 색 이름과 기록
→ Hue Room 아이템·색 보관함·Hueprint 축적
→ 스토리·방·Relay 카드 공유
→ 다음 색을 발견하러 돌아오기
```

이 루프에서 빠지는 기능은 별도 앱처럼 느껴질 가능성이 높다. 새 기능은 `발견`, `수집`, `표현`, `회고`, `관계` 중 하나 이상을 분명히 강화해야 한다.

## 5. 확정된 전체 제품 결정

### 5.1 컬러 헌트와 3x3

- 중앙에는 오늘의 미션 색을 둔다.
- 사용자는 주변에서 그 색과 비슷하다고 느끼는 대상 사진을 찾아 주변 8칸을 채운다.
- 사진의 실제 RGB를 자동 추출해 정답을 판정하지 않는다.
- 색 매칭률과 퍼센트를 제품 UI에서 제거한다.
- `발견한 색`의 데이터 기준은 사진 분석값이 아니라 저장된 `mission_hex`다.
- 3x3은 Hueday를 한눈에 설명하는 대표 결과물로 유지한다.

### 5.2 산책이 아닌 일상 전체

- 서비스의 중심 문구는 `오늘의 색 발견`과 `일상 속 컬러 헌트`다.
- 컬러 산책은 없애지 않고 여러 미션 팩 중 하나로 둔다.
- 집, 학교, 캠퍼스, 통학, 대중교통, 카페, 편의점, 도서관, 회사, 여행, 날씨, 시간, 관심사에서 색을 찾는다.
- 위치 추적을 하지 않아도 미션 팩을 사용할 수 있어야 한다.
- 날씨와 시간은 추천 근거이지 사용 제한이 아니다.

### 5.3 부담 없는 지속 구조

- 연속 일수보다 누적 발견과 유연한 주간 목표를 중심으로 한다.
- 사용자는 한 주 2일·3일·5일 같은 색 리듬을 선택할 수 있다.
- 하루나 한 주를 놓쳐도 누적 색, 아이템, 챕터는 줄지 않는다.
- `기록이 끊겼어요`보다 `새 색이 기다리고 있어요` 같은 복귀 문구를 사용한다.
- 공개 순위, 친구 스트릭, 보상 회수, 소멸 재화는 넣지 않는다.

### 5.4 Hue Room

- 사용자가 발견한 미션 색으로 실제 아이템이 생기는 개인 공간을 만든다.
- 아이템은 처음 얻은 `탄생 색`을 기억한다.
- 이후 발견 색이 늘어나면 기존 아이템도 다른 색으로 다시 칠할 수 있다.
- 색은 소모하지 않고 여러 아이템에 반복 적용할 수 있다.
- 색상마다 아이템 이미지를 만들지 않고 동적 SVG로 색을 합성한다.
- 방과 아이템은 사용자가 쉬는 동안 망가지거나 시들지 않는다.
- 아이템은 원본 3x3 기록과 일기로 돌아가는 기억의 입구가 된다.
- 상세 기준은 `docs/hue-room-product-spec.md`를 따른다.

### 5.5 Hueprint와 Color Capsule

- Hueprint는 저장된 색을 주간·월간·계절·연간 단위로 보여 주는 개인 색 정체성이다.
- 월간 Hueprint는 대표 색, 완성한 3x3, 자주 사용한 색 이름, 대표 사진을 9:16 결과물로 만든다.
- Hueprint는 Hue Room의 포스터·벽지와 연결한다.
- Color Capsule은 과거 색 기록을 시간이 지난 뒤 다시 만나는 회고 기능이다.
- 빈 날을 실패로 표시하지 않고 기록된 날과 색을 중심으로 보여 준다.
- 감정이나 성격을 AI가 단정하는 진단 문구는 사용하지 않는다.

### 5.6 Color Relay

- 사용자가 오늘의 컬러 카드나 미션 링크를 친구에게 보낸다.
- 받은 사람은 로그인 없이 제한된 카드와 `나도 이 색 찾기`를 볼 수 있다.
- 저장·동기화가 필요할 때 가입한다.
- 두 사용자의 결과는 점수나 일치율 없이 나란한 색 조각, 엽서, 공동 팔레트로 보인다.
- 공유 링크는 만료·폐기가 가능하고 위치·EXIF·내부 사용자 ID·다른 비공개 기록을 노출하지 않는다.
- 댓글, 좋아요 수, 팔로워, 공개 검색은 첫 출시 핵심이 아니다.

### 5.7 실제로 쓰는 보상

- 배지는 잠금/해제 아이콘만 보여 주는 장식이 아니다.
- 보상은 Hue Room 아이템, 공간 영역, 스토리 프레임, Hueprint 포스터, Relay 타일처럼 실제로 쓸 수 있어야 한다.
- 기존 사용자의 3·7·14·30 보상은 새 체계로 옮길 때 회수하지 않는다.
- 무료로 획득한 보상은 유료 팩이 생겨도 완성된 무료 아이템으로 남는다.
- 세부 기준은 `docs/colorwalk-reward-system.md`를 따른다.

## 6. 아직 사용자 승인 또는 실험이 필요한 결정

다음은 방향을 정했지만 구현 전에 증거가 더 필요한 항목이다.

| 결정 게이트 | 현재 후보 | 확정 방법 |
| --- | --- | --- |
| 1장과 8장의 의미 | 1장은 진행 시작, 8장은 한 페이지 완성과 주요 보상 | 홈·카메라·저장·복귀 프로토타입 비교 |
| Hue Room 메인 스타일 | Soft Paper Diorama 1순위 | 430x932 세 시안 사용자 선택 |
| Hue Room 진입 | `나` 탭 중심 또는 프로필 내 전체 화면 | 와이어프레임과 기존 내비게이션 QA |
| Hue Chapter 명칭·임계값 | 색 발견자 → Hue Keeper | 실제 진행 속도와 카피 테스트 |
| 출시 기본 아이템 수 | 고품질 16개 목표 | 5개 렌더 스파이크와 제작 속도 확인 |
| 첫 분석 도구 | 최소 이벤트만 우선 | 개인정보·비용·PWA/Android 호환 비교 |
| Color Relay의 무가입 범위 | 카드 보기와 첫 촬영 미리보기 | 보안·저장 경계 프로토타입 |

결정 게이트가 남았다는 이유로 전체 작업을 멈추지 않는다. 게이트 전에 안전하게 할 수 있는 구조 파악·와이어프레임·렌더 스파이크·테스트 설계를 먼저 한다.

## 7. 기능 체계

### A. 오늘의 색 발견

목적: 앱을 열 이유와 현실을 바라볼 작은 과제를 제공한다.

- 날씨·시간·계절 기반 기본 미션
- 사용자가 상황에 맞는 미션 팩 선택
- 중앙 미션 색과 색 이름
- `오늘의 색 찾기` 단일 핵심 CTA
- 촬영 후 그날 미션 고정
- 위치 권한 거부 시에도 사용할 수 있는 fallback

### B. 3x3 컬렉션

목적: 단일 사진보다 Hueday다운 수집과 완성감을 만든다.

- 중앙 미션 색 + 주변 8장
- 촬영·앨범·네이티브 카메라 대체 경로
- 임시 초안과 복구
- 사진별 교체와 순서
- 8칸 완성 상태의 명확한 보상
- 부분 진행을 허용한다면 같은 날 이어 채우는 복귀 경로

### C. 저널과 색 이름

목적: 색에 개인적인 의미를 붙인다.

- 추천 색 이름
- 사용자가 직접 붙이는 이름
- 짧은 문장과 선택적 일기
- 글쓰기를 강제하지 않음
- 색·날짜·미션 팩과 함께 저장

### D. 스토리와 공유 결과물

목적: 발견을 외부에서 한눈에 이해되는 결과로 만든다.

- 3x3 중심 9:16 템플릿
- 미션 색, 이름, 날짜, 짧은 문장
- 범용 편집기보다 Hueday 고유 프레임
- 다운로드, Web Share, 네이티브 공유 fallback
- 일치율과 정확도 표현 제거
- 보상으로 얻은 프레임·스탬프를 실제 사용

### E. 미션 팩

목적: 산책하지 않는 날에도 일상에서 색을 찾게 한다.

초기 정적 팩:

- 집
- 학교·캠퍼스
- 통학·대중교통
- 카페·편의점
- 시간대
- 날씨
- 패션·음식·문구·인테리어
- 컬러 산책
- 계절·여행

처음에는 코드의 정적 config로 만들고 운영에서 자주 교체해야 한다는 증거가 생길 때만 DB/CMS로 옮긴다.

### F. 색 리듬과 보상

목적: 놓친 날의 불안을 만들지 않고 자주 돌아올 이유를 제공한다.

- 주간 2/3/5일 선택 목표
- 평생 누적 발견일
- 완성한 3x3 수
- 경험한 미션 팩
- 월간 참여
- Hue Room/Story/Hueprint 실제 아이템 해금

### G. Hue Room

목적: 저장된 색을 개인 공간과 소유 가능한 정체성으로 바꾼다.

- 동적 SVG 아이템
- 발견 색 보관함
- 탄생 색과 현재 색
- 재채색, 배치, 보관
- 원본 기록 연결
- 월간 포스터와 방 공유

### H. Hueprint와 Capsule

목적: 시간이 흐를수록 앱을 떠나기 어려운 개인 기록 가치를 만든다.

- 주간 대표 색
- 월간 9:16 리캡
- 계절 챕터
- 과거 기록 재발견
- Hue Room 배경·포스터

### I. Color Relay와 가까운 관계

목적: 공개 피드 없이 색 발견 행동이 다음 사용자에게 이어지게 한다.

- 안전한 공유 링크
- `나도 이 색 찾기`
- 공동 팔레트·엽서·짝 타일
- 이후 2~8명 close circle
- 공개 비교·랭킹 없음

### J. 프로필과 색 정체성

목적: 팔로워 수가 아니라 사용자가 모은 색과 기억을 보여 준다.

- Hue Room
- 누적 팔레트
- Hue Chapter
- 자주 붙인 색 이름
- 획득 아이템·미션 팩
- 월간/계절 Hueprint

## 8. 첫 사용과 반복 사용 여정

### 첫 사용

1. Hueday가 무엇인지 한 문장으로 이해한다.
2. 오늘의 미션 색을 본다.
3. 권한과 가입 때문에 마법의 순간이 지나치게 늦어지지 않게 한다.
4. 첫 색 사진을 찍는다.
5. 3x3이 채워지는 경험과 완성 의미를 이해한다.
6. 기록을 저장한다.
7. 첫 Hue Room 변화나 명확한 진행 보상을 본다.
8. 원하면 스토리 또는 링크를 공유한다.

### 반복 사용

1. 오늘 상황에 맞는 미션 팩을 고른다.
2. 새로운 색을 발견하고 기록한다.
3. 방에 새 아이템·새 색·Hueprint 변화가 생긴다.
4. 과거 아이템을 다른 색으로 바꾸거나 기록을 다시 본다.
5. 주간 색 리듬과 미션 팩이 부담 없이 진행된다.

### 돌아온 사용자

- 스트릭 파손 화면을 먼저 보여 주지 않는다.
- 마지막 기록과 방은 그대로 기다린다.
- 오늘 할 수 있는 가장 작은 색 발견을 제안한다.
- 쉬었던 기간을 벌점이나 결손으로 만들지 않는다.

## 9. 비주얼 브랜드

전체 제품은 다음 감각을 유지한다.

- 부드럽고 감정적이지만 유아적이지 않음
- 10대·20대가 공유하고 싶을 만큼 트렌디함
- 따뜻한 아이보리, 세이지, 제한된 코랄 포인트
- 사진과 발견 색이 주인공
- 티켓·컬러 카드·종이 기록의 촉감
- 과도한 그림자, 유리 효과, 무거운 게임 HUD 금지
- 화면별 서로 다른 유행 스타일을 섞지 않음

Hue Room은 `Soft Paper Diorama`를 1순위로 검증하고, 픽셀은 기본 정체성이 아닌 선택적 레트로 스킨으로만 검토한다.

## 10. 개인정보와 안전

- 모든 개인 기록은 기본 비공개다.
- Browser code에는 Supabase publishable key만 둔다.
- service role은 Edge Function 또는 로컬 관리 도구에만 둔다.
- RLS는 owner 기준으로 유지하고 모든 새 테이블을 cross-user denial까지 검증한다.
- 공유 링크는 최소 필드, 만료, 폐기, 짧은 signed URL을 사용한다.
- 정확한 위치, EXIF, 내부 사용자 ID, 다른 비공개 기록을 공유하지 않는다.
- 미성년 사용자에게 공개 DM, 위치 탐색, 공개 인기 순위를 성급히 열지 않는다.
- 분석 이벤트에 사진, 일기 원문, 정확한 위치, 비밀번호 관련 정보를 넣지 않는다.
- 계정 삭제·데이터 export·복구 정책을 유료 장기 보관 전에 완성한다.

## 11. 수익화 원칙

베타에는 광고와 코어 유료벽을 넣지 않는다.

무료로 유지:

- 기본 미션과 미션 팩
- 3x3 촬영·기록·히스토리
- 기본 Hue Room과 발견 색 재채색
- 기본 Hueprint와 스토리 공유
- Color Relay 참여
- 활동으로 획득한 기본 보상

검증 뒤 판매 후보:

- 계절·여행·졸업·커플 Creative Pack
- Hue Room 프리미엄 공간 스킨과 장식 팩
- 고급 Hueprint·연간 리포트·인쇄용 결과물
- 장기 원본 백업과 기기 간 복구를 포함한 Plus
- 엽서·미니북·연간 컬러 북
- 미술관·카페·축제·캠퍼스 B2B 미션 팩
- 사용자가 선택하는 명시적 브랜드 컬러 미션

수익화 도입 조건과 가격 가설은 `docs/product-growth-strategy.md`의 `Monetization Model`을 따른다.

## 12. 성공 지표

### 활성화

- 앱 진입 → 미션 확인
- 미션 확인 → 첫 사진
- 첫 사진 → 저장 또는 3x3 완성
- 저장 → 첫 Hue Room 변화 확인

### 반복 사용

- D1/D7/D30 복귀
- 주간 저장일과 색 리듬 달성
- 완성 3x3 수
- Hue Room 재방문·재채색
- Hueprint 열기와 과거 기록 재방문

### 성장

- 스토리/방/카드 공유율
- 공유 링크 열기
- `나도 이 색 찾기` 시작
- Relay 결과 완성

### 품질

- 권한 거부율
- 초안 복구 성공
- 이미지 업로드·저장 실패
- 방 상태 저장·복구 실패
- 공유 내보내기 실패
- PWA/Android 핵심 여정 성공

숫자는 충분한 세션이 쌓이기 전 가설로 기록하고 사실처럼 부풀리지 않는다.

## 13. 첫 완성 출시 패키지

출시 전 필수 성공 요소:

- 중앙 미션 색 + 주변 8장의 명확한 3x3 규칙
- 사진 색 추출·매칭률 없는 컬러 헌트
- 산책에 국한되지 않는 초기 일상 미션 팩
- 가입·권한·촬영·초안·저장·복구 안정성
- 최소 행동 퍼널 측정
- 실제 아이템을 여는 비처벌형 색 리듬과 보상
- 한 개의 완성도 높은 Hue Room과 발견 색 재채색
- 월간 Hueprint와 최소 Color Capsule 회고
- 안전한 Color Relay 공유 링크와 `나도 이 색 찾기`
- Hueday 고유 9:16 스토리·방 공유 결과물
- PWA와 Android 전체 핵심 여정 QA
- Supabase owner RLS·cross-user denial·데이터 손실 검증

난도 때문에 후순위:

- 공개 무한 피드와 팔로워 경쟁
- 실시간 공동 방 편집
- 3D 방과 아바타·펫 시스템
- 아이템 거래소·랜덤 뽑기·복잡한 코인 경제
- 대규모 close circle 동기화
- 익명 지역 색 트렌드와 운영 CMS
- 고급 네이티브 Instagram 전용 통합
- iOS 네이티브 출시는 Mac 빌드 환경과 실기기 QA 준비 뒤 진행

## 14. 기술 원칙

- 현재 React/Vite/TypeScript, Zustand, Supabase, Capacitor, `html2canvas`를 우선 재사용한다.
- 패키지나 추상화를 추가하기 전에 기존 helper, 웹 표준, 네이티브 플랫폼 기능을 확인한다.
- DB에 파생 가능한 색과 통계를 무작정 중복 저장하지 않는다.
- 정적 미션·아이템 카탈로그는 운영상 원격 수정 필요가 생기기 전 코드 config로 둔다.
- 새 DB 구조에는 migration, owner RLS, cross-user denial 검증, rollback/compatibility 계획이 필요하다.
- 화면 변경은 430x932 캡처와 기존 목업 비교를 통과해야 한다.
- 구현 완료는 코드 존재가 아니라 테스트·빌드·브라우저/Android QA·문서 정합성으로 판단한다.
