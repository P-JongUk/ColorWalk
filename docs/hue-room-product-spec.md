# Hue Room 제품·디자인 명세

마지막 합의 정리: 2026-07-22 KST
문서 역할: Hue Room의 제품 경험, 디자인 언어, 보상 연결, 기술 경계를 정하는 source of truth
구현 상태: 기획 확정 단계. 아직 제품 코드와 DB에는 구현되지 않음
상위 제품 기준: `docs/hueday-product-blueprint.md`
상위 실행 단계: `docs/hueday-development-roadmap.md`의 M4~M5

## 1. 한 문장 정의

> 사용자가 일상에서 발견한 미션 색이 자기만의 아이템으로 태어나고, 모은 색으로 계속 바꾸며 가꾸는 개인 컬러 아카이브 공간.

Hue Room은 별도의 꾸미기 미니게임이 아니다. Hueday의 기존 핵심 행동인 `오늘의 미션 색 확인 → 현실에서 비슷한 색 찾기 → 3x3 기록 완성`이 장기적인 개인 공간과 색 정체성으로 이어지는 결과 화면이다.

## 2. 결정 상태

### 확정된 제품 결정

- 중앙에는 오늘의 **미션 색**을 유지하고, 사용자는 주변 8칸에 그 색과 비슷하다고 느낀 현실의 대상을 촬영한다.
- 첫 사진은 안전하게 저장되는 `오늘의 색 씨앗`이자 진행 시작이며, 8장을 모두 채운 3x3을 오늘의 한 페이지와 미션 완료로 본다.
- 8장 완성은 Hue Room 아이템·Hueprint·완성형 공유 결과물의 주요 보상 시점이다. 부분 진행은 손실 없이 나중에 이어 채울 수 있어야 한다.
- 사진에서 실제 색을 자동 추출해 정답을 판정하지 않는다.
- 색 일치율과 매칭 퍼센트는 사용자에게 보여주지 않는다.
- Hue Room에서 `내가 발견한 색`은 사진 분석값이 아니라 저장된 기록의 `mission_hex`다.
- 완성한 색 기록은 Hue Room 아이템 또는 아이템을 여는 진행도로 이어진다.
- 아이템은 처음 획득한 색을 `탄생 색`으로 기억하고, 사용자는 이후 자신이 발견한 다른 색으로 다시 칠할 수 있다.
- 색은 소모되지 않는다. 한 번 발견한 색을 여러 아이템에 자유롭게 적용할 수 있다.
- 색상별 아이템 이미지를 미리 만들지 않는다. 아이템 형태 하나와 HEX 색상을 실행 중 합성한다.
- 서비스 전체 언어는 `산책에서만 색 찾기`가 아니라 `일상에서 색 발견하기`다. 컬러 산책은 여러 미션 팩 중 하나다.
- 매일 연속 기록을 놓쳤다는 이유로 사용자가 포기하지 않게 한다. 누적 발견과 유연한 주간 목표를 중심으로 설계한다.
- Hue Room의 디자인은 부가 장식이 아니라 제품 가치이므로, 아이템 하나마다 형태·색 역할·축소 가독성·배치·모션·출처 연결을 검수한다.

### 시안과 사용성 검증 뒤 확정할 항목

- 메인 미술 방향: 현재 1순위는 `Soft Paper Diorama`지만, 430x932 시안 비교 후 최종 확정한다.
- `나` 탭을 Hue Room 중심 화면으로 바꿀지, 프로필 안에서 전체 화면으로 진입할지 와이어프레임으로 비교한다.
- 출시 아이템 수는 숫자보다 품질을 우선한다. 기본 목표는 4개 배치 영역에 최소 16개의 완성도 높은 아이템이다.
- Hue Chapter의 명칭과 해금 임계값은 프로토타입에서 진행 속도를 확인한 뒤 확정한다.

## 3. 제품 원칙

### 3.1 발견이 먼저다

사용자는 방을 꾸미기 위해 앱 안에서 반복 탭을 하는 것이 아니라, 일상에서 색을 발견한다. Hue Room의 모든 주요 보상은 저장된 실제 기록으로부터 나온다.

### 3.2 정답보다 해석이다

미션 색과 완벽히 같은 RGB를 찾는 게임이 아니다. 사용자가 `이것도 오늘의 파랑처럼 느껴진다`고 선택하는 관찰과 해석이 핵심이다.

### 3.3 압박보다 축적이다

- 방과 아이템은 접속하지 않아도 망가지거나 사라지지 않는다.
- 캐릭터나 식물이 아프고 시드는 죄책감 설계를 넣지 않는다.
- 연속 기록이 끊겼다는 빨간 실패 화면을 만들지 않는다.
- 레벨과 획득 기록은 내려가지 않는다.
- 돌아온 사용자에게는 `새 색이 기다리고 있어요`처럼 다시 시작하기 쉬운 문구를 쓴다.

### 3.4 표현이 보상이다

배지 숫자, 코인, 공격력보다 사용자가 실제로 배치하고 다시 칠하고 공유할 수 있는 아이템이 보상이다.

### 3.5 한 사람만으로도 완성된다

친구 기능이 없어도 방은 충분히 가치 있어야 한다. Color Relay는 나중에 엽서나 공동 컬러 타일을 더하는 보조 관계 루프다.

## 4. 전체 경험 루프

```text
상황에 맞는 미션 팩 선택
→ 중앙의 미션 색 확인
→ 첫 비슷한 색을 찾아 오늘의 색 씨앗으로 안전하게 저장
→ 당일 또는 나중에 이어서 주변 8칸 채우기
→ 완성된 3x3 한 페이지와 미션 저장
→ 아이템/공간 진행도 해금
→ 발견 색으로 아이템 배치·재채색
→ 아이템에서 원본 3x3과 일기 다시 보기
→ 월간 Hueprint와 Hue Room 스냅샷 공유
→ 새로운 색과 미션 팩을 찾으러 돌아오기
```

## 5. 핵심 용어와 데이터 의미

| 용어 | 의미 | 저장 기준 |
| --- | --- | --- |
| 미션 색 | 그날 중앙에 제시된 색 | `posts.mission_hex` |
| 오늘의 색 씨앗 | 첫 사진을 안전하게 보존한 미완성 진행 | M1에서 확정할 부분 진행 저장 상태 |
| 완성 페이지 | 중앙 미션 색과 주변 사진 8장이 모두 채워진 3x3 | M1에서 확정할 완료 상태와 원본 기록 ID |
| 발견 색 | 사용자가 현실에서 찾아 기록한 미션 색 | 사진 추출값이 아닌 `mission_hex` |
| 탄생 색 | 아이템을 처음 얻었을 때 연결된 발견 색 | 아이템 획득 당시 HEX와 기록 ID |
| 현재 색 | 사용자가 나중에 아이템에 적용한 발견 색 | 배치 상태의 HEX |
| 색 보관함 | 사용자가 저장한 서로 다른 발견 색 목록 | 우선 `posts`에서 파생 계산 |
| 아이템 원본 | 색칠 가능한 SVG 형태와 고정 속성 | 앱의 정적 아이템 registry |
| 아이템 인스턴스 | 사용자가 실제로 획득·배치한 아이템 | 사용자 room state |
| 색 리듬 | 연속 일수가 아닌 유연한 주간 발견 목표 | 저장된 날짜와 선택 목표에서 계산 |

색 보관함을 위해 같은 색 데이터를 별도 테이블에 중복 저장하지 않는다. 첫 구현은 기존 `posts.mission_hex`와 `posts.local_date`를 source of truth로 사용한다.

## 6. 색 리듬과 보상 구조

### 6.1 일일 스트릭을 주인공으로 두지 않는다

사용자는 한 주에 2일, 3일, 5일 중 생활에 맞는 목표를 고를 수 있다. 화면은 `이번 주 색 발견 2/3`처럼 표시한다. 목표를 채우지 못해도 평생 누적 색, 완성한 3x3, 열린 아이템은 유지된다.

권장 진행 축:

- 즉시: 첫 사진을 색 씨앗으로 안전하게 저장하고 칸 채움에 작은 시각·촉각 피드백
- 한 기록: 3x3 한 페이지와 미션 완성, 주요 보상 연결
- 한 주: 선택한 색 리듬 달성
- 한 팩: 학교·집·통학·카페 같은 미션 팩 컬렉션 완성
- 한 달: 월간 Hueprint와 방 배경/포스터
- 장기: Hue Chapter와 새로운 배치 영역

### 6.2 보상의 실제 형태

| 행동 | 보상 후보 | 원칙 |
| --- | --- | --- |
| 첫 색 씨앗 | 저장 확인과 이어하기 표시 | 주요 아이템 해금과 혼동하지 않음 |
| 완성된 3x3 누적 | Hue Room 아이템·가구·소품 선택권 | 연속 일수가 아닌 누적 완성도 인정 |
| 주간 색 리듬 | 장식, 재질, 작은 공간 효과 | 실패해도 기존 보상 회수 금지 |
| 미션 팩 완성 | 해당 생활 문맥의 대표 아이템 | 학교·카페·통학 등 기록과 연결 |
| 월간 참여 | Hueprint 포스터·벽지 | 연속이 아닌 월 안의 유연한 참여 |
| Color Relay | 두 사람의 엽서·짝 컬러 타일 | 순위와 친구 스트릭 금지 |

기존 3·7·14·30 배지는 마이그레이션 전까지 호환 표시를 유지할 수 있지만, 최종 의미는 `연속 일수 배지`가 아니라 누적 발견·완성·리듬을 통해 실제 아이템을 여는 단계로 바꾼다. 이미 획득한 사용자의 보상은 회수하지 않는다.

## 7. Hue Room의 정보 구조

### 권장 1차 구조

- `나` 탭 상단 또는 메인 화면: 방 전체와 이번 달 팔레트
- 방 캔버스: 벽, 창문, 선반, 책상, 바닥의 고정 배치 영역
- 하단 트레이: `아이템`, `색상`, `기록`
- 설정과 계정 정보: 방을 가리지 않는 보조 화면 또는 상단 메뉴

### 핵심 조작

- 아이템 탭: 이름, 탄생 색, 획득 계기, 원본 3x3 기록 열기
- 길게 누르기 또는 `색 바꾸기`: 내가 발견한 색 보관함 열기
- 드래그: 같은 유형의 허용된 배치 슬롯 사이 이동
- 숨기기: 보관함으로 되돌리되 소유권과 탄생 기록은 유지
- 되돌리기: 탄생 색으로 복원
- 공유: 현재 방을 9:16 이미지로 내보내기

초기 버전은 자유 좌표와 물리 충돌 대신 검증된 배치 슬롯을 사용한다. 사용자가 의도하지 않은 겹침, 작은 화면 조작 실패, 저장 복잡도를 줄이기 위한 결정이다.

## 8. 비주얼 디자인 방향

### 8.1 1순위 시안: Soft Paper Diorama

완전한 정면 2D보다 약간의 깊이가 있지만, 복잡한 3D나 전형적인 아이소메트릭 게임은 아닌 `종이로 만든 작은 컬러 스튜디오`를 목표로 한다.

- 따뜻한 아이보리와 세이지 계열의 조용한 기본 공간
- 종이를 오린 듯한 둥근 실루엣과 완만한 곡선
- 순수 검정 외곽선 대신 짙은 웜 그레이 또는 면 분리
- 얕은 그림자와 제한된 하이라이트
- 한 장의 재사용 가능한 미세 종이 질감
- 고해상도 사진·스토리 카드와 충돌하지 않는 벡터 선명도
- 발견 색이 가장 강한 시각적 포인트가 되도록 기본 방은 중립적으로 유지

### 8.2 픽셀 디자인 판단

픽셀 아트는 메인 스타일로 고정하지 않는다. 픽셀 방, 작은 아바타, 방명록, 배경음악, 친구 방 방문이 결합되면 싸이월드 미니홈피 복제품으로 보일 위험이 크고 현재 Hueday의 부드러운 고해상도 사진·티켓·여백과도 충돌한다.

픽셀은 향후 다음 용도로만 검토한다.

- 기간 한정 레트로 스킨
- Y2K 미션 팩의 공유 카드
- 특별 이벤트용 아이템 렌더 스타일

### 8.3 Hueday만의 방으로 만드는 요소

일반적인 침대·소파 꾸미기만으로는 차별화되지 않는다. 방을 `Color Archive Studio`로 해석한다.

- 완성한 3x3을 넣는 벽 액자
- 미션 색 카드를 꽂는 컬러 선반
- 날짜가 적힌 티켓 보관함
- 카메라와 필름통
- 색 유리병과 팔레트 러그
- 월간 Hueprint 포스터
- Color Relay로 받은 엽서
- 학교·집·카페·통학 미션 팩 기념품

## 9. 요소별 디자인 계약

모든 아이템은 아래 항목을 정의하고 검수한다.

| 항목 | 필수 결정 |
| --- | --- |
| 역할 | 왜 사용자가 이 아이템을 얻고 싶어 하는가 |
| 출처 | 어떤 미션 팩·누적 행동·기록에서 열리는가 |
| 실루엣 | 430x932 화면의 실제 배치 크기에서도 알아볼 수 있는가 |
| 색 영역 | `base`, `light`, `shadow`, `fixed`, 필요 시 `accent` |
| 극단 색 | 흰색·검정·고채도·저채도에서도 형태가 유지되는가 |
| 배치 | 벽·선반·책상·바닥 중 어디에 놓이는가 |
| 상태 | 잠김, 새로 획득, 배치됨, 선택됨, 보관됨 |
| 상호작용 | 탭, 길게 누르기, 이동, 원본 기록 열기 |
| 모션 | 새로 나타날 때와 선택할 때 필요한 최소 동작 |
| 접근성 | 색만으로 상태를 구분하지 않는가, 터치 영역이 충분한가 |
| 공유 | 9:16 스냅샷에서 잘리지 않고 의미가 남는가 |

### 출시 기본 아이템 구성 목표

아이템 수보다 각 배치 영역의 완성감을 우선하되, 한 방을 충분히 꾸밀 수 있도록 다음 16개를 첫 목표로 삼는다.

- 벽 4개: 3x3 액자, Hueprint 포스터, 거울, 컬러 티켓 보드
- 선반 4개: 색 유리병, 책 더미, 카메라, 작은 라디오
- 책상 4개: 조명, 머그잔, 연필꽂이, 엽서 스탠드
- 바닥 4개: 러그, 화분, 스툴, 작은 수납함

학교·통학·카페·집·날씨 미션 팩은 이 기본 형태를 무작정 복제하지 않고, 기록 맥락이 느껴지는 한정 아이템을 단계적으로 추가한다.

## 10. 동적 색상 렌더링

### 10.1 조합 폭발을 피하는 원칙

`아이템 N개 × 색상 M개` 이미지를 만들지 않는다. 아이템 SVG는 한 번만 만들고 색상 값만 바꾼다.

아이템 색 역할:

```text
base    = 사용자가 선택한 발견 색
light   = base와 흰색을 혼합한 밝은 면
shadow  = base와 따뜻한 어두운 색을 혼합한 그림자
fixed   = 금속, 유리, 전구, 외곽선처럼 유지되는 부분
accent  = 필요한 아이템에만 쓰는 보조 포인트
```

정확한 미션 HEX는 색 보관함과 아이템의 대표 면에 보존한다. 큰 가구 전체에는 같은 색을 부드럽게 섞어 방이 고채도 색으로 난잡해지지 않게 한다.

### 10.2 권장 구현

- 아이템 정의는 우선 앱 코드의 정적 registry에 둔다.
- 렌더링은 React 인라인 SVG를 사용한다.
- 색 조합은 기존 `src/lib/colors.ts`를 재사용하고, 필요한 최소 `mixHex`/톤 생성 helper만 추가한다.
- SVG에는 내보내기 호환성을 위해 계산이 끝난 HEX를 `fill` 값으로 전달한다.
- 질감은 아이템마다 PNG를 만들지 않고 한 개의 종이 노이즈/패턴을 재사용한다.
- 외부 SVG 문자열을 위험하게 주입하거나 색상별 파일을 Supabase Storage에 저장하지 않는다.

SVG의 `fill`, gradient, pattern, mask는 브라우저에서 널리 지원된다. 구현 시 기준 자료:

- https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Attribute/fill
- https://developer.mozilla.org/en-US/docs/Web/SVG/Tutorials/SVG_from_scratch/Gradients
- https://developer.mozilla.org/en-US/docs/Web/SVG/Tutorials/SVG_from_scratch/Patterns
- https://developer.mozilla.org/en-US/docs/Web/SVG/Tutorials/SVG_from_scratch/Clipping_and_masking

## 11. 데이터와 저장 설계

### 11.1 첫 구현의 최소 구조

아이템 카탈로그는 정적 코드로 유지하고, 사용자별 상태만 저장한다.

```ts
type RoomItemPlacement = {
  instanceId: string
  itemId: string
  sourcePostId?: string
  unlockKey: string
  originalColor: string
  currentColor: string
  slotId: string
  rotation?: number
}

type RoomState = {
  version: 1
  roomStyle: 'paper-studio'
  items: RoomItemPlacement[]
  updatedAt: string
}
```

첫 DB 후보는 사용자당 한 행인 `room_states`다.

- `user_id uuid primary key references auth.users`
- `state jsonb not null`
- `updated_at timestamptz`
- owner 전용 RLS

베타에서 동시 편집 충돌이 실제로 발생하기 전에는 아이템별 테이블과 복잡한 동기화 계층을 만들지 않는다. 다중 기기 충돌이 측정되면 `updated_at` 기반 충돌 감지 또는 행 단위 정규화를 검토한다.

### 11.2 검증 규칙

- `itemId`, `slotId`, `unlockKey`는 허용 목록에 있는 값만 저장한다.
- 색상은 `^#[0-9A-Fa-f]{6}$` 형식만 허용한다.
- `currentColor`는 원칙적으로 사용자의 저장된 발견 색 중 하나여야 한다.
- 다른 사용자의 room state는 읽거나 수정할 수 없다.
- `sourcePostId`를 통해 다른 사용자의 비공개 기록이 노출되지 않게 한다.
- 향후 공유 스냅샷은 방 전체 이미지와 최소 공개 정보만 제공하고 원본 기록 탐색을 허용하지 않는다.

## 12. 미션 팩과 아이템 연결

Hueday의 기본 표현은 `오늘의 색 발견`이다. `컬러 산책`은 장소 팩 하나로 남긴다.

| 미션 문맥 | 예시 미션 | 아이템 계열 |
| --- | --- | --- |
| 집 | 집 안에서 가장 따뜻한 베이지 | 조명, 쿠션, 화분, 러그 |
| 학교·캠퍼스 | 교실에서 오늘의 청록 찾기 | 연필꽂이, 노트, 책, 게시판 |
| 통학·대중교통 | 유리와 금속 속 파랑 찾기 | 창문 장식, 승차권, 헤드폰 |
| 카페·편의점 | 살구색 또는 갈색 발견하기 | 머그잔, 의자, 작은 테이블 |
| 비 오는 날 | 숨어 있는 회색 찾기 | 우산, 빗방울 창문, 물웅덩이 조명 |
| 밤 | 보라와 남색 찾기 | 달 조명, 커튼, 무드등 |
| 컬러 산책 | 동네의 초록을 한 페이지에 모으기 | 지도 카드, 운동화, 식물 |

정확한 위치를 요구하지 않고 사용자가 현재 상황에 맞는 팩을 선택하게 한다. 날씨·시간은 추천 근거이지 참여 제한이 아니다.

## 13. Hue Chapter

숫자 레벨은 보조 정보로만 두고 표현 범위가 넓어지는 챕터를 사용한다.

- 색 발견자
- 색 수집가
- 팔레트 메이커
- 무드 큐레이터
- Hue Keeper

진행도는 발견한 날, 완성한 3x3, 경험한 미션 팩, Hueprint, Color Relay처럼 서로 다른 행동을 종합한다. 같은 행동을 짧은 시간에 반복해 진행도를 파밍하는 구조는 피한다. 챕터는 절대 내려가지 않으며 큰 챕터 변화는 선반·벽·책상·창문 같은 표현 영역을 연다.

명칭과 정확한 임계값은 구현 전에 사용자에게 보이는 카피 시안과 함께 확정한다.

## 14. 공유와 회고 연결

- 방 전체를 9:16 `이번 달 나의 색방` 이미지로 내보낸다.
- 월간 Hueprint를 방의 포스터 또는 벽지로 적용할 수 있다.
- 아이템을 탭하면 탄생한 3x3 기록과 일기를 다시 볼 수 있다.
- Color Relay가 구현되면 친구가 보낸 색은 방 안의 엽서나 짝 컬러 타일로 남는다.
- 공유 이미지에는 위치, 내부 사용자 ID, 다른 비공개 기록으로 가는 경로를 넣지 않는다.

첫 구현부터 아래 이벤트 이름과 의미를 정의하되, 분석 도구 선택은 별도 측정 계획을 따른다.

## 16. 접근성·성능·QA 기준

### 접근성

- 색만으로 잠김·선택·새 아이템 상태를 구분하지 않는다.
- 아이템 터치 영역은 작은 SVG 실루엣보다 넓게 잡는다.
- 색 이름과 HEX를 함께 제공한다.
- 움직임 줄이기 설정에서 등장·흔들림 애니메이션을 줄인다.
- 아주 밝거나 어두운 색에서도 아이템 경계와 텍스트 대비를 유지한다.

### 성능

- 방 진입 시 사용자 사진 원본을 한꺼번에 읽지 않는다.
- 아이템 원본은 정적 SVG로 묶고 색상별 래스터 파일을 만들지 않는다.
- 방 스냅샷은 사용자가 내보낼 때 생성한다.
- 저사양 Android와 PWA에서 첫 방 표시 시간과 드래그 반응을 확인한다.

### 필수 시각 QA

- 기준 크기: 430x932
- 상태: 빈 방, 절반 배치, 가득 배치, 아이템 선택, 색 보관함, 잠금/새 보상
- 색 극단: 흰색에 가까운 색, 검정에 가까운 색, 고채도 빨강·파랑, 저채도 중립색
- 플랫폼: Chrome/PWA, Android WebView, 공유 이미지 결과
- 비교 기준: `.design-references/00-target-mockup/`의 여백·타이포·부드러운 티켓 감성
- Hue Room 전용 시안과 캡처는 `.design-references/05-hue-room/`에 로컬 보관하고 Git에는 넣지 않는다.
