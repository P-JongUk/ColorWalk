# Hueday 저장·동기화·비용 전략

마지막 갱신: 2026-07-23 KST
상태: 제품·아키텍처 기준 확정, 구현 전
목표: 사용자가 늘어도 사진 트래픽과 DB 비용을 통제하면서 기록 손실과 기기 변경 불안을 막는다.

## 1. 결론

Hueday는 **로컬 우선 + 작은 필수 클라우드 + 선택형 유료 고화질 백업** 구조를 사용한다.

- 모든 사진을 매번 클라우드에서 다시 내려받는 구조를 기본으로 하지 않는다.
- 로컬에만 두고 복구 수단이 전혀 없는 구조도 사용하지 않는다.
- DB에는 통계와 복구에 필요한 작은 구조화 데이터만 상시 저장한다.
- 고화질 사진 보관과 기기 간 자동 복구처럼 반복 비용이 드는 기능은 `Hueday Cloud`로 분리한다.
- 사용자의 기록과 저화질 미리보기는 구독 해지로 갑자기 사라지거나 잠기지 않는다.

## 2. 데이터 계층

| 계층 | 저장 항목 | 기본 위치 | 비용 원칙 |
| --- | --- | --- | --- |
| 로컬 원본 | 촬영한 고화질 사진, 편집 전 원본, Hue Canvas 작업 상태, 썸네일 캐시 | Capacitor Filesystem + 초기에는 IndexedDB 메타데이터 | 네트워크 없이 열고 편집 |
| 무료 작은 클라우드 | 계정, 프로필, 날짜, `mission_hex`, 색 이름, 짧은 일기, 완료 상태, 그리드 manifest, Hue Palette 수량, 작은 3x3 미리보기, Hue Canvas compact recipe | Supabase Database/Storage | 동기화와 통계에 필요한 최소량 |
| 유료 고화질 클라우드 | 고화질 사진 파생본, 기기 간 복구용 archive, 고화질 작품 백업, 휴지통 | Supabase Storage 또는 비용 비교 후 호환 스토리지 | 명확한 용량 한도와 구독으로 반복 비용 회수 |
| 파생 산출물 | Story, Hueprint, 고해상도 Canvas export | 필요할 때 로컬 재생성 | 같은 결과를 여러 해상도로 영구 중복 저장하지 않음 |
| 임시 전송 | `.hueday` 암호화 archive, 신규 기기 이전 파일 | OS Files/Drive 또는 TTL 서버 업로드 | 검증·복구 완료 전 원본 삭제 금지 |

Color Hunt의 최소 기록 계약은 `local_date`, 당시 기기 시간대, 잠긴 `mission_hex`, 사진 수, `recorded/completed` 상태를 구분한다. 첫 사진부터 그날의 유효한 기록이며 8장만 완료 3×3과 주요 보상으로 계산한다. 현지 자정에는 1–7장도 현재 상태로 닫아 보존하고 다음 날 새 기록을 만들며, 새 초안이 전날 기록을 덮어쓰거나 전날 색을 오늘의 활성 미션으로 이월해서는 안 된다.

## 3. 사진 품질 정책

현재 구현은 최대 1440px, 목표 약 420KB, 최소 품질 0.6의 WebP 압축본을 업로드한다. 달력 썸네일과 3x3 미리보기에는 효율적이지만 유일한 장기 원본으로 쓰기에는 품질 손실 위험이 있다.

앞으로는 한 번의 파괴적 압축이 아니라 목적별 파생본을 사용한다.

1. **로컬 마스터**
   - 기기에서 보존하는 가장 좋은 품질.
   - 사용자가 명시적으로 공간 정리를 선택하기 전에는 자동 삭제하지 않는다.
2. **무료 미리보기**
   - 달력과 작은 3x3 표시에 충분한 작은 WebP.
   - 클라우드 트래픽을 줄이고 빠르게 내려받는다.
3. **공유 산출물**
   - Story/Hueprint를 만들 때 로컬 마스터와 recipe에서 생성한다.
4. **Cloud 고화질 백업**
   - 단일 고정 420KB보다 긴 변의 크기·품질 하한·최대 파일 크기를 함께 사용한다.
   - 실제 사진 샘플의 시각 비교 뒤 2048~2560px 계열을 시작 가설로 측정한다.

원칙: 압축 전에 원본과 파생본의 역할을 구분하며, 확인되지 않은 압축본을 사용자의 유일한 사본으로 만들지 않는다.

## 4. 로컬 저장 구현 순서

### 1단계

- 기존 웹/PWA 호환을 위해 IndexedDB에 구조화 메타데이터를 둔다.
- Capacitor Android에서는 Filesystem에 사진과 큰 binary를 둔다.
- 저장 경로를 앱 내부 ID로 추상화하고 OS 절대 경로를 DB에 영구 저장하지 않는다.
- 로컬 manifest에 checksum, 크기, MIME, 생성일, cloud 상태를 둔다.

### 2단계

- 기록 수와 검색 요구가 실제로 IndexedDB 한계를 만들 때만 SQLite를 검토한다.
- SQLite 도입 전 migration·백업·웹 이중 구현 비용을 측정한다.
- 단순한 로컬 파일 + IndexedDB로 충분하면 새 의존성을 추가하지 않는다.

## 5. 동기화 규칙

- 로컬 저장은 사용자 입력 직후 성공해야 하고 네트워크를 기다리지 않는다.
- 네트워크 동기화는 큐에서 재시도한다.
- 서버에는 `version`, `updated_at`, device ID 또는 client mutation ID를 둔다.
- 구조화 메타데이터 충돌은 마지막 쓰기만 덮는 대신 두 버전을 보존하거나 사용자에게 선택권을 준다.
- 사진 업로드는 checksum으로 중복을 피한다.
- Hue Canvas는 타일을 칠할 때마다 쓰지 않고 디바운스된 로컬 snapshot과 주기적 compact cloud snapshot을 사용한다.
- 삭제는 즉시 영구 삭제보다 tombstone/휴지통 단계를 거친다.
- 새 기기 복구를 확인하기 전 기존 기기나 임시 서버 사본을 삭제하지 않는다.

## 6. 수동 기기 이전

무료 사용자도 데이터 이동 수단이 있어야 한다.

- 설정에서 암호화된 `.hueday` archive를 내보낸다.
- OS 공유 시트나 Files/Drive에 사용자가 직접 보관한다.
- 새 기기에서 archive를 가져오고 checksum·schema version을 검증한다.
- 사진·기록 개수와 미리보기를 보여 준 뒤 복구한다.
- 복구 성공과 사용자 확인 뒤에만 임시 전송 파일을 지운다.
- 서버를 경유한다면 짧은 TTL, 1회 토큰, 암호화, 용량 제한을 적용한다.

무료 이전 경로를 없애고 Cloud 구독만 강제하지 않는다.

## 7. 분석 데이터

제품 통계를 위해 사진 원본을 DB에 저장할 필요는 없다.

허용하는 최소 이벤트:

- 미션 노출
- 촬영 시작
- 첫 사진 기록과 미션 색 잠금
- 같은 날 2–7장 추가 및 현지 자정 기록 마감
- 3x3 완료
- 저널 저장
- Hue Canvas 생성·재방문·내보내기
- Story/Hueprint export
- 공유 링크 열기
- 백업 성공·실패

수집하지 않는 항목:

- 사진 픽셀 또는 자동 추출 색
- 일기 본문
- 정확한 GPS
- Hue Canvas 전체 셀 내용
- 연락처·개인 메시지

이벤트는 가능하면 사용자별 일일 요약으로 묶고, 원시 로그는 30~90일 보관 뒤 집계·삭제하는 방안을 기본 가설로 둔다.

## 8. 비용 방어선

- 달력 목록은 고화질 원본이 아니라 작은 preview를 요청한다.
- 목록 스크롤마다 signed URL을 재발급하지 않고 안전한 범위에서 캐시한다.
- 이미지 크기와 MIME을 업로드 전 검증한다.
- 동일 파일 checksum 중복 업로드를 막는다.
- 무제한 백업 표현을 사용하지 않는다.
- Hueday Cloud는 초기 5GB 한도를 가설로 두고 사용량을 사용자에게 보여 준다.
- 캐시·egress·storage를 상품별 공헌이익에 포함한다.
- AI 도안 생성처럼 요청당 비용이 생기는 기능은 1회 구매 Studio에 무제한 포함하지 않는다.
- 분석·로그는 사진보다 작더라도 무기한 원시 보관하지 않는다.

2026-07-23 공식 가격표를 기준으로 Supabase Pro 포함량은 file storage 100GB, cached/uncached egress 각 250GB이며 초과 단가는 storage $0.0213/GB-month, cached egress $0.03/GB, uncached egress $0.09/GB로 안내된다. 가격은 바뀔 수 있으므로 결제 도입·대규모 베타 직전에 다시 확인한다.

- 가격: <https://supabase.com/pricing>
- egress 계산: <https://supabase.com/docs/guides/platform/manage-your-usage/egress>

### 공급자 역할 결정

- 출시와 초기 성장 단계의 주 데이터 계층은 Supabase Auth·Postgres·RLS·Storage로 유지한다. 이미 검증된 인증·소유자 권한·서명 이미지 접근을 Railway로 선제 이전하지 않는다.
- Cloudflare R2는 지금 추가하지 않는다. Hueday Cloud 출시가 확정되고 Supabase 저장량 또는 전송량이 포함 한도의 70~80%에 접근하거나 실제 비용 측정에서 분리 이익이 확인될 때, 고화질 백업 객체만 옮기는 후보로 검토한다. 메타데이터와 소유권 기준은 Supabase에 둔다.
- Railway는 주 DB나 인증 대체재가 아니라 이미지 변환, 예약 작업, 알림처럼 앱 요청과 분리된 장시간 서버 작업이 실제로 필요할 때만 보조 실행 환경으로 검토한다.
- Neon·Firebase·Appwrite 등으로의 전체 이전은 현재 병목이 없으므로 보류한다. 공급자 교체는 추측이 아니라 비용·성능·지역·규제 한계가 측정된 뒤 결정한다.
- 이식성을 위해 표준 Postgres migration, 공급자에 종속되지 않는 object key와 메타데이터를 유지하되, 아직 필요하지 않은 다중 공급자 추상화는 만들지 않는다.

## 9. 수익화 연결

### 무료

- 현재 기기의 고화질 로컬 기록
- 작은 클라우드 메타데이터와 preview
- 수동 `.hueday` 내보내기/가져오기
- 기본 Hue Canvas recipe 복구

### Hueday Cloud 가격 가설

- 월 1,500원
- 연간 출시 가설 9,900원, 가치가 확인된 뒤 정상가 12,000원 검토
- 5GB 고화질 백업
- Wi-Fi 자동 백업
- 기기 간 자동 복구
- 클라우드 고화질 다시 받기
- 30일 휴지통
- 저장 공간 사용량 표시

### 해지

- 새 고화질 업로드를 중단한다.
- 유예 기간과 export 경로를 제공한다.
- 작은 메타데이터·미리보기·로컬 기록은 유지한다.
- 해지를 이유로 사용자의 유일한 사본을 즉시 삭제하지 않는다.

## 10. 현재 구현과 차이

현재 코드는 완성/부분 기록의 압축 WebP들을 Supabase Storage에 올리고, 라이브 `grid_images` migration이 없으면 `client_meta.gridImages`로 fallback한다. 따라서 아래는 아직 구현 전이다.

- 고화질 로컬 마스터 보존 계약
- 작은 무료 preview와 고화질 Cloud 계층 분리
- 수동 `.hueday` archive
- offline-first 동기화 큐와 충돌 처리
- Hue Canvas compact recipe
- 유료 용량·휴지통

문서는 목표 구조이며 현재 상태를 구현 완료로 해석하지 않는다.

## 11. 구현 게이트

1. 저장 대상별 데이터 분류와 schema version 확정
2. 기존 기록 무손실 migration·rollback 계획
3. 앱 종료·오프라인·업로드 실패 복구 테스트
4. 저화질/고화질 샘플 시각 QA
5. 기기 변경 archive 복구 테스트
6. owner RLS·cross-user denial
7. 사용자당 월 storage/egress 비용 측정
8. 계정 삭제와 데이터 export 완성
