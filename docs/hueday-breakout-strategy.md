# Hueday Breakout Strategy

마지막 코드 대조: 2026-07-22 KST
문서 성격: 현재 구현, 시장 근거, 제품 가설을 분리해서 관리하는 living document
전체 제품 합의: `docs/hueday-product-blueprint.md`
전체 실행 순서: `docs/hueday-development-roadmap.md`

## 한 문장 방향

> Hueday는 오늘의 미션 색을 일상에서 발견해 3x3으로 모으고, 그 색으로 나만의 공간과 색 정체성을 키우는 카메라 기반 컬러 다이어리다.

경쟁 앱의 알림, 피드, 위젯, 미니홈피를 그대로 복제하지 않는다. Hueday가 소유해야 할 경험은 `오늘의 미션 색을 현실에서 발견하는 순간`, `그 색이 Hue Room 아이템이 되는 순간`, `모인 색이 Hueprint가 되는 순간`이다.

## 문서를 읽는 법

- **확인됨**: 2026-07-22 현재 코드나 공식 자료에서 확인한 사실이다.
- **해석**: 확인된 사실을 바탕으로 한 제품 판단이다.
- **실험**: 아직 검증되지 않은 제안이다. 사용자 행동 데이터로 채택 여부를 결정한다.
- 시장 수치와 외부 서비스 기능은 시간이 지나면 바뀐다. 인용 날짜와 원문을 다시 확인한 뒤 갱신한다.

### 아직 구현되지 않은 것

- 공유 이미지를 본 사람이 앱으로 돌아오는 공개 안전 링크나 딥링크
- 초대, 친구, close circle, 공동 미션, 공개/비공개 피드
- 월간 Hueprint 결과물과 자동 회고 카드
- 배지가 스토리 프레임·스탬프를 실제로 여는 기능
- Hue Room, 발견 색 보관함, 동적 색상 아이템, 재채색, 방 상태 저장
- 연속 일수 중심이 아닌 주간 Color Rhythm과 누적 보상
- 제품 행동 분석 이벤트와 전환 퍼널
- 결제, 구독, 광고, 스폰서 미션 운영 도구
- iOS Capacitor 패키지, `ios/` 프로젝트, TestFlight/App Store 파이프라인
- 가입부터 저장·공유까지의 컴포넌트 통합 테스트나 실제 브라우저 E2E

### 운영상 남아 있는 부채

- 라이브 Supabase에 `posts.grid_images` 마이그레이션이 없을 때 `client_meta.gridImages`로 자동 대체한다. 데이터 손실을 막는 좋은 호환 장치지만 영구 구조로 굳히면 안 된다.
- 승인된 제품 계약은 1컷을 안전하게 저장되는 `오늘의 색 씨앗`, 8컷을 오늘의 미션과 한 페이지 완성으로 본다. 그러나 촬영 완료 조건은 여전히 `images.length > 0`이므로 현재 구현은 부분 저장과 최종 완료를 구분하지 못한다.
- 배지 문구는 창작 보상을 약속하지만 현재는 잠금/해제 표시뿐이고 사용할 아이템과 연결되지 않는다.
- `src/index.css`가 약 9,800줄인 단일 스타일 파일이다. 지금 당장 전면 재작성할 이유는 없지만 화면 실험 속도와 회귀 위험을 계속 관찰해야 한다.
- 단위 테스트는 핵심 helper를 잘 보호하지만 사용자가 체감하는 `가입 → 촬영 → 저장 → 공유` 연결은 자동 검증하지 않는다.

## 2. 냉정한 진단

### 좋은 재료는 이미 많다

- 색 미션은 일반 사진 일기보다 행동을 구체적으로 만든다.
- 현실에서 색을 찾게 하므로 앱 안 스크롤이 아니라 밖을 보는 경험을 만든다.
- 3x3과 9:16 결과물은 수집성과 공유성을 동시에 갖는다.
- 원본 얼굴 중심 SNS가 아니어서 비교 피로와 사생활 노출을 줄일 수 있다.
- 날씨·시간 문맥, 색 이름, 짧은 문장, 달력은 시간이 쌓일수록 개인적 가치가 커진다.

### 그러나 지금 상태로 대성공하기 어려운 이유

1. **첫 마법의 순간이 너무 늦다.** 가입 정보 입력, 권한, 여러 장 촬영, 이름과 일기, 스토리 편집을 거쳐야 완성품을 본다.
2. **핵심 규칙이 선명하지 않다.** 8장을 채우는 게임인지, 한 장만 기록해도 되는 일기인지 코드와 카피가 다르게 말한다.
3. **공유가 유통으로 이어지지 않는다.** 지금의 결과물은 예쁘지만 파일로 끝난다. 받은 친구가 같은 미션을 해볼 통로가 없다.
4. **쌓임의 보상이 약하다.** 달력과 숫자는 있지만 “내가 어떤 색의 사람인지”를 보여주는 독점적 결과물이 아직 없다.
5. **배지 약속이 미완성이다.** 보상은 보이지만 실제 창작 도구가 열리지 않아 기대가 행동으로 돌아오지 않는다.
6. **측정 장치가 없다.** 어디에서 이탈하고 무엇 때문에 돌아오는지 모르면 디자인 취향으로 우선순위를 정하게 된다.
7. **현재 편집기는 코어보다 앞서 있다.** 템플릿과 스티커가 풍부한데, 첫 저장과 재방문을 증명하기 전에 편집 선택지가 커졌다.

가장 큰 문제는 기능 부족이 아니다. `한 번 써보면 친구에게 설명하고 싶은 단 하나의 경험`이 아직 제품 전면에 고정되지 않은 것이다.

## 3. Hueday가 소유할 제품 개념

### A. Color Hunt: 오늘의 색 발견

**실험 가설:** 사용자는 “일기를 써라”보다 “오늘의 살구색을 주변에서 찾아라”처럼 작고 구체적인 탐색에 더 쉽게 반응한다.

- 홈의 가장 큰 행동은 `오늘의 색 찾기` 하나로 둔다.
- 중앙에는 미션 색을 유지하고 사용자는 그 색과 비슷하다고 느끼는 대상을 주변 8칸에 모은다.
- 사진에서 실제 색을 추출하거나 일치율로 정답을 판정하지 않는다.
- 첫 사진을 찍으면 미션 색 티켓과 3x3 진행이 즉시 반응한다.
- 첫 결과물은 앱을 연 뒤 60초 안에 보여주는 것을 목표로 한다.
- 1컷은 안전하게 저장되는 `첫 색 발견`이자 `오늘의 색 씨앗`이며, 진행 시작이지 오늘 기록이나 미션의 최종 완료가 아니다.
- 8컷을 모두 채우면 오늘의 미션과 중앙 미션 색을 포함한 `오늘의 한 페이지`가 완성된다.
- 8컷은 당일에 강제하지 않는다. 사용자는 미완성 진행을 잃지 않고 나중에 이어 채울 수 있다.
- 미완성 상태에 실패, 보상 손실, 연속 일수 초기화, 죄책감 표현을 사용하지 않는다.
- Hue Room 아이템, Hueprint, 완성형 공유 결과물 같은 주요 보상은 완성된 3x3을 중심으로 연결한다.

이 의미는 2026-07-22 게이트 1에서 확정했다. 현재 코드가 1장부터 저널 진입·저장·초안 복구를 지원하는 사실은 1장 완료의 근거가 아니라 B안에서 부담 없는 중간 저장과 이어하기를 구현할 수 있는 기반이다. 제품 계약과 다른 현재 완료 처리·카피·보상 분기는 M1 후속 구현 부채로 분리한다.

### B. Hueprint: 색으로 쌓이는 나의 흔적

**실험 가설:** 사람은 개별 기록보다 기록이 모여 자신을 설명해 줄 때 오래 남는다.

- 일주일: `이번 주에 자주 발견한 세 가지 색`
- 한 달: 색 띠, 시간대, 날씨, 짧은 문장을 조합한 `월간 Hueprint`
- 계절: `봄의 나`, `장마의 나`, `시험 기간의 나` 같은 컬러 챕터
- 1년: 영상 대신 색과 3x3으로 재생되는 연간 컬러 필름
- 프로필: 팔로워 수가 아니라 누적 팔레트와 내가 자주 붙인 색 이름을 보여준다.

Hueprint는 다른 SNS가 쉽게 복제하기 어려운 Hueday의 장기 데이터 자산이 된다. 단, 성격이나 정신 상태를 단정하는 진단 문구는 피하고 사용자가 해석할 여지를 남긴다.

### C. Color Relay: 비교 없는 친구 유입

**실험 가설:** 친구의 사진에 반응하라고 하기보다 같은 색을 자기 주변에서 찾게 하면 콘텐츠 생산과 초대가 한 동작이 된다.

1. 사용자가 오늘의 컬러 카드를 링크로 공유한다.
2. 친구는 로그인 없이 제한된 카드만 본다.
3. 가장 큰 버튼은 `나도 이 색 찾기`다.
4. 친구는 계정 없이 로컬에서 첫 사진과 미리보기까지 경험한다.
5. 저장·동기화할 때만 가입한다.
6. 두 사람에게는 점수나 승패 없이 서로 찾은 색 조각만 나란히 보인다.

공개 피드가 없어도 카드 하나가 다음 촬영을 만들기 때문에 Hueday만의 작은 네트워크 효과가 생긴다.

### D. Color Capsule: 시간이 지나야 열리는 회고

- 오늘 저장한 기록 일부를 30일 뒤 다시 보여준다.
- 친구와 함께한 색 릴레이는 월말에 한 장의 공동 팔레트로 묶는다.
- “연속 30일”만 보상하지 않고 “이번 달 서로 다른 12색 발견”처럼 실패감이 적은 수집 목표를 함께 둔다.
- 놓친 날에는 빨간 실패 표시 대신 빈 페이지를 그대로 남겨 다음 색을 시작하게 한다.

### E. Hue Room: 발견한 색으로 자라는 나의 공간

**확정 방향:** 사용자가 저장한 미션 색이 실제 방 아이템의 탄생 색이 되고, 새로운 색을 발견할수록 기존 아이템도 다시 칠할 수 있게 한다.

- 색상별 아이템 이미지를 만들지 않고 한 SVG와 동적 HEX 톤을 사용한다.
- 아이템은 탄생 색과 원본 3x3 기록을 기억한다.
- 색은 소모되지 않고 여러 아이템에 사용할 수 있다.
- 방은 접속하지 않아도 망가지거나 시들지 않는다.
- 기본 디자인은 Soft Paper Diorama를 1순위로 시안 검증하고, 픽셀은 기본이 아닌 선택적 레트로 스킨으로만 검토한다.
- 누적 발견, 완성 3x3, 미션 팩, 주간 Color Rhythm, 월간 Hueprint가 실제 방 아이템과 영역을 연다.

상세 제품·디자인·데이터 기준은 `docs/hue-room-product-spec.md`, 구현 순서는 `docs/hue-room-development-roadmap.md`를 따른다.

## 4. 가장 단순한 실행 순서

이 절의 Phase 설명은 전략 배경이다. 실제 현재 단계, 다음 한 작업, 기능별 완료 조건은 `docs/hueday-development-roadmap.md`를 유일한 실행 상태판으로 사용한다.

아래 Phase는 3개월 일정이 아니라 의존 순서다. 현재 목표는 속도를 위해 Hueday의 성공 요소를 삭제하는 최소 베타가 아니라, Phase 0의 제품 진실·측정, Phase 1의 Color Relay, Phase 2의 Hueprint·실제 배지 보상까지 실사용 가능한 첫 버전으로 완성한 뒤 최대한 빨리 출시하는 것이다. Color Capsule은 Hueprint와 함께 구현 가능한 최소 회고부터 포함한다. Phase 3의 close circle과 Phase 4의 사업 확장처럼 운영·동기화·심사 난도가 큰 항목만 효과 대비 난도를 근거로 후순위화한다.

### Phase 0 — 제품 진실 맞추기와 측정

먼저 새 소셜 기능이 아니라 현재 코어의 약속을 정렬한다.

1. `1컷 기록 / 8컷 완성` 규칙을 사용자 테스트로 결정하고 모든 카피·버튼·배지 계산을 일치시킨다.
2. 첫 결과물을 가입 뒤가 아니라 가입 전 로컬 체험으로 보여주는 프로토타입을 만든다. 서버 익명 계정은 다시 열지 않는다.
3. 저장 전 스토리 편집을 선택 사항으로 뒤로 보내 첫 저장 시간을 줄인다.
4. 최소 이벤트를 정의한다: `mission_viewed`, `capture_started`, `first_photo_taken`, `journal_saved`, `grid_completed`, `story_exported`, `share_opened`, `relay_started`.
5. 실제 이벤트 수집 전에도 베타 인터뷰에서 각 단계의 시간과 이탈 이유를 수기로 기록한다.

초기 내부 성공 기준은 업계 평균이 아니라 **100명 또는 300개 유효 세션 뒤 다시 정할 실험 기준**이다.

| 지표 | 첫 실험 기준 |
| --- | --- |
| 앱 진입 → 첫 사진 | 중앙값 60초 이내 |
| 첫 사진 → 첫 저장 | 70% 이상 |
| 첫 저장 다음 날 재방문 | 35% 이상 |
| 첫 주 3일 이상 저장 | 가입자의 20% 이상 |
| 저장 → 이미지/링크 공유 | 20% 이상 |
| 공유 링크 열기 → 같은 미션 시작 | 10% 이상 |

### Phase 1 — 공유 가능한 오늘의 색

- 공개 안전 `shared_cards` 한 장과 만료·폐기 가능한 slug를 만든다.
- 링크에는 위치, EXIF, 내부 사용자 ID, 다른 기록 탐색을 넣지 않는다.
- 수신자는 로그인 없이 카드를 보고 `나도 이 색 찾기`를 누를 수 있다.
- 먼저 카카오톡·인스타그램 DM·문자에서 링크 미리보기와 430x932 화면을 검증한다.
- 댓글, 좋아요, 팔로워, 공개 검색은 만들지 않는다.

### Phase 2 — Hue Room·Hueprint와 실제 보상

- 현재 월간 helper를 이용해 클라이언트 9:16 월간 리캡부터 만든다.
- 누적 발견·완성 3x3·Color Rhythm을 실제 Hue Room/스토리/Hueprint 무료 아이템에 연결하고 기존 3·7·14·30 보상을 무손실로 옮긴다.
- 발견 색으로 아이템이 태어나고 다시 칠할 수 있는 Hue Room의 한 방을 완성한다.
- 배지를 누르면 해당 기간의 색과 사진을 보고 바로 스토리로 만들 수 있게 한다.
- 리캡이 저장·재방문·공유를 늘리는지 확인한 뒤 서버 캐시나 AI 문구를 검토한다.

### Phase 3 — 작은 그룹의 공동 색

- 공개 피드보다 2~8명 close circle 하나로 시작한다.
- 모두 같은 날 같은 색을 찾고, 결과는 얼굴 피드가 아니라 색 조각 보드로 보인다.
- “누가 먼저/더 비슷하게” 같은 순위는 넣지 않는다.
- 개인 기록만으로도 제품 가치가 유지되어야 한다. 친구가 없으면 빈 소셜 화면이 되는 구조는 금지한다.

### Phase 4 — 문화와 사업 확장

- 카페, 미술관, 축제, 학교 동아리와 기간 한정 미션 팩을 시험한다.
- 충분한 표본과 동의가 있을 때만 익명 집계 `이번 주 서울이 발견한 색`을 만든다.
- 물리 엽서·미니 포토북·연간 컬러 북은 Hueprint가 실제로 공유되는지 확인한 뒤 시험한다.

## 5. 지금 만들지 않을 것

- 공개 무한 피드, 팔로워 수, 인기 순위
- 코어 기록을 막는 첫 화면 유료벽
- 베타 광고와 행동을 방해하는 전면 광고
- AI가 사용자의 감정이나 성격을 단정하는 기능
- 정확한 위치 기반 사용자 탐색
- 고급 영상 편집기나 범용 Canva 경쟁 기능
- 데이터 없이 모든 기능을 한 번에 만드는 대규모 백엔드
- 리텐션이 증명되기 전의 코인, 포인트, 복잡한 레벨 시스템

## 6. Setlog는 어떻게 돈을 버는가

### 확인된 사실

- Setlog는 같은 날 소규모 친구들이 각자 짧은 영상을 올리고 하나의 그룹 vlog로 묶는 앱이다.
- 2026-07-22 확인한 한국 App Store 페이지는 앱을 무료로 표시하며, 공개된 인앱 구입 항목이나 구독 상품을 보여주지 않는다.
- 공식 사이트와 이용약관에서도 광고·구독·유료 상품을 주 수익원으로 명시한 공개 자료를 찾지 못했다.

따라서 현재 공개 자료만으로는 “Setlog가 특정 방식으로 이미 돈을 번다”고 단정할 수 없다. 무료 앱의 운영비가 투자금, 창업자 자금, 제휴, 아직 공개되지 않은 사업 계약 중 무엇에서 나오는지도 확인되지 않았다. **현재 관찰되는 전략은 수익 최적화보다 사용량과 네트워크 확장을 우선하는 성장 단계**라는 해석까지가 안전하다.

### Hueday가 배울 점

- Setlog의 강점은 영상 편집 기능이 아니라 여러 사람의 아주 작은 행동이 하나의 결과물로 합쳐지는 구조다.
- 시간 제한 완화, 최대 친구 수 조정, 묶음 보기 같은 업데이트는 핵심 제작 부담을 줄이고 공동 결과물을 키우는 방향이다.
- 반대로 리뷰에서 보이는 안정성, 연락처 탐색, 레이아웃 변경 불만은 소셜 기능보다 촬영·업로드 신뢰성과 사용자의 기존 습관 보존이 먼저라는 경고다.

## 7. Hueday의 수익 모델

이 절은 수익화 방향의 상위 요약이다. 실제 상품 범위, 출시 조건, 측정 지표의 source of truth는 `docs/product-growth-strategy.md`의 `Monetization Model` 절이다.

### 원칙

1. 처음에는 기록과 친구 유입을 무료로 둔다.
2. 사용자의 사진이나 불안을 인질로 삼지 않는다.
3. 돈은 `더 예쁘게 만들기`, `더 오래 보존하기`, `특별한 맥락에서 함께하기`에서 번다.
4. 배지로 번 무료 보상은 유료화 뒤에도 실제 가치가 있어야 한다.
5. 광고는 규모가 생긴 뒤에도 일상 피드가 아니라 명확히 표시된 브랜드 미션처럼 제품 문맥에 맞게 제한한다.

### 추천 순서

| 시점 | 모델 | 무료로 남길 것 | 유료 가치 | 시작 조건 |
| --- | --- | --- | --- | --- |
| 베타 | 전부 무료 | 미션, 촬영, 기록, 히스토리, 기본 공유 | 없음 | 코어 리텐션 측정 |
| 초기 | 1회 구매 팩 | 기본 템플릿과 획득 배지 보상 | 계절·여행·커플·졸업 팔레트, 한정 프레임 | 공유/리캡 사용자가 반복 구매 의향을 보일 때 |
| 성장 | Hueday Plus | 기본 기록과 로컬/기본 클라우드 사용 | 장기 원본 백업, 연간 Hueprint, 고급 내보내기, 기기 간 복구 | 반복적인 서버 비용과 월간 가치가 생겼을 때 |
| 성장 | 실물 상품 | 디지털 리캡 | 엽서, 월간 미니북, 연간 컬러 북 | 리캡 저장·공유가 충분할 때 |
| 확장 | B2B 미션 팩 | 일반 일일 미션 | 미술관·카페·축제·캠퍼스의 기간 한정 색 산책 | 커뮤니티 파일럿에서 참여율을 증명했을 때 |
| 대규모 | 명시적 스폰서십 | 개인 기록 화면의 평온함 | 선택형 브랜드 컬러 미션 | 대규모 활성 사용자와 브랜드 안전 기준이 있을 때 |

가격은 제품 가치가 확인된 뒤 A/B가 아닌 소규모 구매 의향 인터뷰부터 시험한다. 첫 탐색 범위로는 1회 팩 1,500~4,900원, Plus 월 3,900원 또는 연 29,000원처럼 이해하기 쉬운 구간을 사용할 수 있으나 확정 가격이 아니다.

### 왜 지금 광고가 아닌가

BeReal은 대규모 활성 사용자 기반을 만든 뒤 네이티브 피드 광고와 하루 takeover를 출시했고, Voodoo는 2025년에 BeReal이 인수 당시 0에서 3,000만 유로 매출로 성장했다고 밝혔다. 이것은 광고가 나쁘다는 뜻이 아니라 **광고가 규모 이후의 모델**이라는 뜻이다. Hueday 베타에서 광고를 넣으면 데이터는 거의 만들지 못하고 첫 감정 경험만 훼손할 가능성이 높다.

인접 앱은 다른 길도 보여준다. Locket은 친한 친구 위젯을 무료로 확산시키고 Gold 인앱 구입을 제공한다. 1 Second Everyday는 누적 회고의 백업·고급 편집·워터마크 제거에 과금한다. Finch는 일일 습관과 창작 보상을 무료 코어 위의 Plus로 확장한다. Hueday에는 `무료 네트워크 루프 + 유료 창작/보존` 조합이 가장 자연스럽다.

## 8. LG Gram에서 iOS App Store에 출시하는 방법

### 현재 상태

- 현재 프로젝트에는 `@capacitor/ios`와 `ios/` 폴더가 없다.
- Windows에서 React/Vite 공통 코드, PWA, Supabase, Android 개발은 계속할 수 있다.
- 네이티브 iOS 빌드·서명·App Store 업로드는 Apple 도구 체인과 macOS 빌드 환경이 필요하다.
- Apple Developer Program은 현재 연 99달러이며, 실제 iPhone QA와 App Review용 개인정보·스크린샷·연령 등급 준비가 필요하다.

### 가능한 경로

| 경로 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| 중고 Mac mini를 빌드 머신으로 사용 | 장기 비용 예측, Xcode/시뮬레이터/서명 직접 제어, 원격 접속 가능 | 초기 구매와 관리 필요 | 꾸준히 iOS를 운영할 1인 개발자에게 가장 추천 |
| Mac 대여 또는 지인 Mac + 이후 클라우드 CI | 초기 비용이 낮고 첫 Xcode 설정 가능 | 사용할 때마다 접근 조율 | 첫 TestFlight 검증용 현실적 선택 |
| Codemagic·Bitrise·GitHub Actions macOS 등 클라우드 빌드 | Windows 중심 개발 유지, 자동 빌드/업로드 | 인증서·프로비저닝 설정이 어렵고 사용량 비용 발생 | 반복 배포 보조로 적합 |
| Xcode Cloud | App Store Connect/TestFlight 통합, Apple 공식 | 최초 workflow 설정과 문제 해결에 Xcode 접근이 사실상 필요 | Mac 초기 설정 뒤 좋은 선택 |
| PWA만 운영 | 지금 바로 iPhone Safari 홈 화면 설치 가능 | App Store 노출·네이티브 기능·심사 배포가 아님 | 베타용 임시 경로일 뿐 최종 App Store 경로 아님 |

### 추천 실행안

1. LG Gram에서 공통 웹 코드와 Android 베타를 계속 개발한다.
2. 핵심 리텐션이 확인되면 Apple Developer Program에 가입한다.
3. 중고 Mac mini 또는 단기 Mac 환경에서 `@capacitor/ios`를 추가하고 최초 Xcode 프로젝트·Bundle ID·서명을 설정한다.
4. 카메라, 위치, 사진 저장, 공유 시트, 알림 권한 문구와 개인정보 처리를 실제 iPhone에서 검증한다.
5. 첫 TestFlight를 통과한 뒤 Xcode Cloud 또는 다른 macOS CI로 반복 빌드를 자동화한다.
6. App Store 심사 전에 계정 삭제, 개인정보처리방침, 데이터 수집 고지, 미성년 사용자 정책을 별도 점검한다.

iOS 플랫폼을 추가할 때의 기본 명령은 Mac 환경에서 `npm install @capacitor/ios`, `npx cap add ios`, `npx cap sync ios`다. 이 명령만으로 출시는 끝나지 않으며 Xcode 서명과 실기기 QA가 필수다.

## 9. 제품 의사결정 기준

새 기능은 아래 질문에 통과해야 한다.

1. 첫 색 발견 시간을 줄이는가?
2. 색 기록이 쌓일수록 개인 가치가 커지는가?
3. 공유받은 사람이 같은 행동을 해보고 싶어지는가?
4. 친구가 없어도 혼자 쓸 가치가 있는가?
5. 사진 원본·외모·인기 비교보다 색과 발견이 중심인가?
6. 미성년 사용자의 위치와 사생활을 기본적으로 보호하는가?
7. 가장 작은 실험으로 가설을 틀렸다고 판정할 수 있는가?
8. 결과를 어떤 이벤트와 사용자 인터뷰로 검증할 것인가?
9. Hueday 전체 청사진의 현재 약속과 마스터 로드맵의 단계에 맞는가?

하나의 기능이 이 질문에 대부분 답하지 못하면 만들지 않거나 더 작게 줄인다.

## 10. 문서 자동 갱신 계약

Codex는 의미 있는 개발 작업이 끝날 때 아래를 작업의 일부로 취급한다.

- 실제 구현이 바뀌면 이 문서의 `현재 제품의 실제 모습`과 로드맵 상태를 대조한다.
- 전체 제품 약속이나 출시 핵심 패키지가 바뀌면 `docs/hueday-product-blueprint.md`를 갱신한다.
- 기능 의존 순서, 현재 단계, 다음 한 작업이 바뀌면 `docs/hueday-development-roadmap.md`를 갱신한다.
- Hue Room 제품·디자인·데이터가 바뀌면 두 Hue Room 문서를 함께 검토한다.
- 제품 방향·우선순위·수익화 가설이 바뀌면 이 문서와 `docs/product-growth-strategy.md`를 함께 갱신한다.
- 촬영·스토리·프로필·보상·수익화가 바뀌면 `docs/colorwalk-reward-system.md`와 보상 helper를 함께 검토한다.
- 배포 환경이나 검증 결과가 바뀌면 `docs/release-readiness.md`를 갱신하되, 과거 검증 날짜를 최신인 것처럼 덮어쓰지 않는다.
- 실제 오류, 어려운 제약, 중요한 트레이드오프를 해결하면 `docs/career-problem-solving-log.md`에 근거와 결과를 남긴다.
- 현재 상태·결정·다음 할 일은 `docs/ai-memory/`에 기록하고 종료 스크립트로 세션 기록과 Graphify를 갱신한다.
- 외부 시장 정보는 원문과 확인 날짜를 남기고, 사실·해석·실험을 섞지 않는다.
- 변경할 내용이 없는 문서는 억지로 수정하지 않고 세션 기록에 `영향 없음`과 이유를 남긴다.
