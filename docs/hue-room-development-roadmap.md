# Hue Room 개발 로드맵

마지막 갱신: 2026-07-22 KST
로드맵 성격: 날짜를 늘여 잡는 일정표가 아니라 재작업을 줄이는 의존 순서
제품·디자인 기준: `docs/hue-room-product-spec.md`
상위 실행 상태: `docs/hueday-development-roadmap.md`의 M4~M5. 이 문서는 그 단계 안의 세부 순서만 관리한다.

## 현재 상태

- 현재 단계: **HR-0 — 제품 규칙과 시각 방향 확정**
- 구현 상태: Hue Room 코드·DB 없음
- 이번 문서화로 완료된 것: 제품 원칙, 동적 색상 방식, 데이터 후보, 디자인 QA 계약, 단계별 완료 기준 정리
- 다음 한 작업: 430x932 기준 세 가지 Hue Room 시안과 핵심 5개 아이템의 형태·색상 프로토타입을 비교하고 메인 방향을 승인받기

## 상태 표기

- `[ ]` 시작 전
- `[-]` 진행 중
- `[x]` 코드·문서·검증까지 완료
- `[!]` 사용자 선택이나 외부 권한이 필요함

단순히 코드가 존재한다는 이유로 완료 처리하지 않는다. 각 단계의 성공 조건과 검증을 모두 통과해야 `[x]`가 된다.

## 전체 의존 순서

```text
HR-0 제품·시각 결정
  ↓
HR-1 동적 SVG 렌더링 스파이크
  ↓
HR-2 방 화면과 배치 상호작용
  ↓
HR-3 저장·복구·RLS
  ↓
HR-4 색 보관함·재채색·원본 기록 연결
  ↓
HR-5 색 리듬·누적 보상·미션 팩
  ↓
HR-6 아이템 콘텐츠 완성·월간 Hueprint
  ↓
HR-7 공유·분석 이벤트·접근성
  ↓
HR-8 전체 회귀·실기기·출시 판정
```

HR-0과 HR-1을 통과하기 전에 16개 아이템 전체를 그리지 않는다. 핵심 5개로 색상·축소 가독성·내보내기 가능성을 증명한 뒤 콘텐츠를 확장한다.

## HR-0 — 제품 규칙과 시각 방향 확정

목표: 코드와 에셋을 대량 제작하기 전에 사용자가 보게 될 핵심 규칙과 디자인 언어를 고정한다.

### 작업

- [x] 중앙 미션 색을 유지하고 사진 색 추출·일치율을 사용하지 않는 결정 기록
- [x] `발견 색 = 저장된 mission_hex` 데이터 의미 기록
- [x] 색상별 이미지 대신 동적 SVG를 사용하는 방향 기록
- [x] 아이템의 탄생 색과 현재 색을 분리하는 방향 기록
- [x] 일상 미션 팩과 비처벌형 색 리듬 방향 기록
- [x] `1장 진행 / 8장 완성`의 최종 의미 결정: 첫 사진은 색 씨앗, 8장 3x3은 한 페이지 완성과 주요 보상
- [ ] Hue Room 진입 구조 비교: `나 탭 중심` 대 `프로필 안 전체 화면`
- [ ] 430x932 시안 세 가지 제작
  - Soft Paper Diorama
  - Minimal Editorial Vector
  - Game-like Soft 2.5D
- [ ] 메인 스타일 1개와 보조 스타일 규칙 승인
- [ ] 기본 방의 벽·선반·책상·바닥 비율 확정
- [ ] 핵심 5개 아이템의 형태 콘셉트 승인: 액자, 조명, 화분, 머그잔, 러그

### 성공 조건

- 사용자가 세 시안을 보고 메인 방향을 명시적으로 선택했다.
- 5개 아이템이 작은 화면에서도 서로 구분되고 Hueday 기존 목업과 시각적으로 충돌하지 않는다.
- 확정 사항과 실험 사항이 `docs/hue-room-product-spec.md`에 구분되어 있다.
- 1장과 8장의 의미가 홈·카메라·저장·보상에서 모순되지 않는다.

### 검증

- `.design-references/00-target-mockup/`과 나란히 430x932 비교
- 흑백 실루엣 테스트와 25% 축소 테스트
- 밝은 색·어두운 색·중립색을 적용한 아이템 비교
- 사용자 승인 내용 기록

### 권장 설정

- 모델: Sol
- 추론: high
- 계획 모드: 켬
- 목표 모드: 전체 출시 목표를 추적 중일 때만 켬

## HR-1 — 동적 SVG 렌더링 스파이크

목표: 색마다 에셋을 만들지 않고 하나의 아이템이 어떤 발견 색에서도 아름답게 보이고 공유 이미지로 저장되는지 증명한다.

권장 브랜치: `feature/hue-room-renderer`

### 작업

- [ ] 기존 `src/lib/colors.ts`를 재사용한 최소 톤 생성 helper 설계
- [ ] `base`, `light`, `shadow`, `fixed` 색 역할 구현
- [ ] 핵심 5개 인라인 SVG 구현
- [ ] 임의 HEX 적용과 즉시 재채색 미리보기
- [ ] 한 개의 재사용 가능한 종이 질감 또는 벡터 패턴 시험
- [ ] 430x932 방 캔버스 프로토타입
- [ ] 기존 StoryStudio 방식 또는 가장 작은 대체 경로로 9:16 이미지 저장 시험
- [ ] 동적 SVG와 Canvas 내보내기의 Android WebView 호환 확인

### 예상 파일

- `src/lib/colors.ts`
M4에서 새로 만들 후보 파일:

- `src/lib/room.ts`
- `src/components/HueRoomPrototype.tsx` 또는 최종 명칭
- `src/index.css`의 Hue Room 전용 구간
- 작은 단위 테스트

새 패키지는 기본적으로 추가하지 않는다. 현재 React, SVG, CSS, `html2canvas`로 성공하지 못한 근거가 있을 때만 검토한다.

### 성공 조건

- 5개 SVG가 임의의 유효 HEX로 즉시 바뀐다.
- 흰색 근처, 검정 근처, 고채도, 저채도 색에서도 형태가 무너지지 않는다.
- 색상별 PNG/SVG 복제 파일이 생기지 않는다.
- 브라우저와 Android에서 방 프로토타입과 9:16 결과가 일치한다.
- 색 helper의 경계값 테스트가 통과한다.

### 검증

- `npm run lint`
- `npm test -- --run`
- `npm run build`
- 430x932 스크린샷 비교
- Android 에뮬레이터 표시·내보내기 QA

## HR-2 — 방 화면과 배치 상호작용

목표: 사용자가 작은 화면에서 아이템을 편하게 보고, 선택하고, 슬롯 사이에 배치할 수 있는 완성된 방 화면을 만든다.

권장 브랜치: `feature/hue-room-layout`

### 작업

- [ ] 방 캔버스와 안전 영역 구현
- [ ] 벽·선반·책상·바닥 배치 슬롯 정의
- [ ] 하단 `아이템 / 색상 / 기록` 트레이 구현
- [ ] 아이템 탭·선택·보관·배치 이동 구현
- [ ] 터치 hit area와 키보드/스크린리더 상태 구현
- [ ] 잠김·새 아이템·배치됨·선택됨 상태 디자인
- [ ] 계정/설정 진입이 Hue Room을 방해하지 않게 정리
- [ ] 잘못된 겹침과 화면 밖 이동 방지

### 성공 조건

- 430x932에서 한 손 조작으로 아이템을 배치·보관할 수 있다.
- 아이템이 겹치거나 사라져 복구할 수 없는 상태가 생기지 않는다.
- 색만 보지 않아도 잠김·선택·새 상태를 이해할 수 있다.
- 기존 오늘·카메라·저널·히스토리 진입을 깨지 않는다.

### 검증

- 컴포넌트 상태 테스트 또는 가장 작은 상호작용 테스트
- Chrome 모바일 뷰포트 QA
- Android 터치 QA
- 디자인 QA 캡처: 빈 방, 절반, 가득 참, 선택 상태

## HR-3 — 저장·복구·RLS

목표: 방 배치가 계정에 안전하게 저장되고 다른 사용자가 읽거나 수정할 수 없게 한다.

권장 브랜치: `feature/hue-room-persistence`

### 작업

- [ ] 최종 `RoomState` 스키마와 version 결정
- [ ] `room_states` migration과 owner RLS 작성
- [ ] 유효한 item/slot/color만 받는 검증 구현
- [ ] 로드·저장·기본 상태·오류 복구 구현
- [ ] 네트워크 실패 시 사용자 변경을 잃지 않는 최소 재시도/로컬 초안 검토
- [ ] 다른 기기 최신 상태 충돌의 베타 정책 문서화
- [ ] Supabase 검증 스크립트에 owner CRUD와 cross-user denial 추가

### 성공 조건

- 새 계정은 안전한 기본 방으로 시작한다.
- 새로고침·로그아웃·재로그인 뒤 배치와 색이 복구된다.
- 익명 사용자와 다른 사용자의 read/write가 거부된다.
- 잘못된 HEX, itemId, slotId가 저장되지 않는다.
- 저장 실패가 조용히 유실되지 않고 사용자가 알 수 있다.

### 검증

- `npm run verify:supabase`
- `npm run lint`
- `npm test -- --run`
- `npm run build`
- 두 사용자 교차 접근 수동 QA

## HR-4 — 색 보관함·재채색·원본 기록 연결

목표: 새 기록이 실제 꾸미기 선택지로 느껴지고, 방의 아이템이 과거 기억으로 돌아가는 입구가 되게 한다.

권장 브랜치: `feature/hue-room-color-library`

### 작업

- [ ] `posts.mission_hex`에서 사용자 색 보관함 파생
- [ ] 중복 색 표시 규칙과 날짜/미션 문맥 정리
- [ ] 아이템 탄생 색과 현재 색 표시
- [ ] 길게 누르기 또는 버튼으로 색 보관함 열기
- [ ] 색 적용·미리보기·취소·탄생 색 복원
- [ ] 아이템에서 `sourcePostId`의 3x3·일기 열기
- [ ] 삭제된 원본 기록을 참조할 때의 안전한 빈 상태
- [ ] 색 이름·HEX·선택 상태 접근성 적용

### 성공 조건

- 저장된 기록이 하나 늘면 색 보관함에 올바르게 반영된다.
- 하나의 발견 색을 여러 아이템에 적용할 수 있고 소모되지 않는다.
- 현재 색을 바꿔도 탄생 색과 획득 기록은 사라지지 않는다.
- 다른 사용자의 기록을 source로 열 수 없다.

### 검증

- 색 보관함 파생 helper 테스트
- 원본 기록 존재/삭제 상태 테스트
- 브라우저·Android 긴 누르기와 하단 시트 QA
- 흰색·검정·중립색 재채색 시각 QA

## HR-5 — 색 리듬·누적 보상·미션 팩

목표: 연속 일수를 놓쳐도 포기하지 않으면서 새 색과 아이템을 계속 찾고 싶은 성장 구조를 만든다.

권장 브랜치: `feature/hue-room-reward-loop`

### 작업

- [ ] 2/3/5일 주간 색 리듬 선택과 진행 표시
- [ ] 기존 3·7·14·30 보상과의 무손실 전환 규칙 확정
- [ ] 누적 발견, 완성 3x3, 미션 팩, 월간 참여 unlock 모델 구현
- [ ] 배지 잠금/해제만 보이던 UI를 실제 아이템 획득으로 연결
- [ ] 놓친 날·주에 실패나 회수 문구를 사용하지 않음
- [ ] 집·학교·통학·카페·날씨·컬러 산책 미션 팩의 첫 정적 config
- [ ] 각 팩과 대표 아이템 연결
- [ ] 기존 사용자에게 이미 획득한 보상을 보존하는 migration/계산 검증

### 성공 조건

- 하루나 한 주를 놓쳐도 누적 진행과 획득 아이템이 줄지 않는다.
- 각 보상은 방에서 바로 보거나 배치할 수 있다.
- 컬러 산책이 유일한 문맥이 아니라 일상 미션 팩 중 하나로 표시된다.
- 기존 사용자 보상이 사라지지 않는다.
- `docs/colorwalk-reward-system.md`와 reward helper가 일치한다.

### 검증

- 누적/주간 경계 날짜 테스트
- 기존 사용자 보상 회귀 테스트
- 미션 팩 선택과 기본 추천 테스트
- 홈·프로필·Hue Room 카피 QA

## HR-6 — 아이템 콘텐츠 완성·월간 Hueprint

목표: 한 방을 자기답게 꾸밀 만큼 충분한 고품질 콘텐츠와 월간 회고 가치를 완성한다.

권장 브랜치: `feature/hue-room-content`

### 작업

- [ ] 기본 16개 아이템 각각 요소별 디자인 계약 작성·검수
- [ ] 아이템별 네 가지 극단 색 테스트
- [ ] 미션 팩 대표 아이템의 출처와 획득 카피 연결
- [ ] 월간 Hueprint를 포스터/벽지로 적용
- [ ] 아이템 보관함의 정렬·새 항목 표시·출처 필터
- [ ] 한 방이 가득 찼을 때도 시각적 위계 유지
- [ ] 에셋 용량과 첫 렌더 성능 측정

### 성공 조건

- 사용자는 한 가지 정답 배치가 아니라 여러 조합을 만들 수 있다.
- 16개 아이템이 Hueday 고유 기록과 연결되고 일반 게임 에셋처럼 보이지 않는다.
- 월간 기록이 방에 눈에 보이는 흔적으로 남는다.
- 저사양 Android에서 사용 불가능한 지연이나 메모리 문제가 없다.

### 검증

- 요소별 디자인 체크리스트 서명
- 빈 방/절반/가득 찬 방 430x932 비교
- 월간 데이터 0개/1개/많음 상태
- 번들 크기와 방 첫 렌더 측정

## HR-7 — 공유·분석 이벤트·접근성

목표: 방을 자랑할 수 있고 실제로 기록과 재방문을 늘리는지 측정할 수 있게 한다.

권장 브랜치: `feature/hue-room-sharing`

### 작업

- [ ] 9:16 방 스냅샷 내보내기
- [ ] 위치·내부 ID·비공개 기록을 제외한 공유 결과 검토
- [ ] Hue Room 핵심 이벤트 계측
- [ ] 아이템 → 원본 기록 → 다시 색 찾기 흐름 연결
- [ ] 움직임 줄이기, 초점, 스크린리더, 터치 영역 점검
- [ ] 공유 실패 시 다운로드 fallback
- [ ] Color Relay가 준비됐으면 엽서/짝 컬러 타일 연결, 아니면 명확히 후속 표시

### 성공 조건

- 공유 이미지가 실제 카카오톡·인스타그램 스토리 크기에서 읽힌다.
- 비공개 원본과 계정 정보가 공유물에 새지 않는다.
- 최소 이벤트로 `기록 → 방 변화 → 공유/회고`를 측정할 수 있다.
- 접근성 기본 조작이 색과 제스처 하나에만 의존하지 않는다.

### 검증

- `npm run lint`
- `npm test -- --run`
- `npm run build`
- 실제 공유 시트/다운로드 QA
- 이벤트 중복·개인정보 payload 점검

목표: Hue Room이 기존 핵심 흐름을 깨지 않고 완성 출시 기준을 통과한다.

### 출시 판정

아래 중 하나라도 실패하면 Hue Room 포함 출시를 완료로 말하지 않는다.

- 사용자 방 상태 또는 원본 기록 연결이 유실됨
- 다른 사용자의 room state나 비공개 기록 접근 가능
- 극단 색에서 아이템 식별 불가능
- Android/PWA에서 배치·재채색·공유 핵심 조작 실패
- 기존 가입·촬영·저장·히스토리·스토리 회귀
- 획득한 보상이 표시만 되고 실제로 사용할 수 없음

## 브랜치와 체크포인트 규칙

- 각 큰 단계는 최신 `main`에서 `feature/<기능명>` 브랜치를 만든다. `codex/` 접두사는 쓰지 않는다.
- 한 커밋에는 렌더러, 저장, 보상, 콘텐츠처럼 하나의 의미 있는 체크포인트만 담는다.
- 커밋 메시지는 한글 conventional prefix를 사용한다.
- 예:
  - `feat: Hue Room 동적 색상 렌더러 추가`
  - `feat: Hue Room 배치 상태 저장과 RLS 적용`
  - `feat: 발견 색 재채색과 원본 기록 연결`
  - `docs: Hue Room 단계 검증 결과 갱신`
- 관련 검증을 통과한 체크포인트만 푸시한다.
- 단계 완료 때 제품 명세, 이 로드맵, 보상 문서, AI memory, 디자인 QA 영향을 함께 확인한다.

## Codex 실행 계약

Hue Room 작업을 시작할 때 Codex는 다음 순서를 따른다.

1. `AGENTS.md`와 `docs/development-reference-guide.md`를 읽는다.
2. `docs/hue-room-product-spec.md`의 확정 결정과 해당 요소별 디자인 계약을 읽는다.

7. 단계별 검증을 실행한다.

9. 의미 있는 디자인 변경은 430x932 캡처와 `docs/design-qa-log.md`를 남긴다.
